# ascelerate

A command-line tool for the App Store Connect API, built with Swift.

## Build & Run

```bash
swift build                           # Debug build
swift build -c release                # Release build (~7 min cold, mostly ASCKit's generated client)
swift run ascelerate <command>        # Run directly
swift run ascelerate --help           # Show all commands
```

Install globally:
```bash
strip .build/release/ascelerate              # Strip debug symbols (~156 MB → ~41 MB)
cp .build/release/ascelerate /usr/local/bin/
```

## Dependencies

- **ASCKit** (local target, `Sources/ASCKit`) — the App Store Connect client, generated by [swift-openapi-generator](https://github.com/apple/swift-openapi-generator) (build plugin) from Apple's own spec, on [swift-openapi-runtime](https://github.com/apple/swift-openapi-runtime) and [swift-openapi-urlsession](https://github.com/apple/swift-openapi-urlsession); see "ASCKit" below. It replaced asc-swift in 0.22.0.
- **AscelerateCore** (local target, `Sources/AscelerateCore`) — the commands' App Store Connect logic, on ASCKit; see "AscelerateCore" below. Both are also library products.
- **[swift-argument-parser](https://github.com/apple/swift-argument-parser)** (1.3.0+) — CLI framework
- **[swift-certificates](https://github.com/apple/swift-certificates)** (1.0.0+) — X.509 certificate and CSR generation (CSRs in AscelerateCore's `Certificates.signingRequest`, used by `certs create`'s auto-CSR flow)
- **[Yams](https://github.com/jpsim/Yams)** (5.0.0+) — YAML parsing (used by `screenshot` command for `ascelerate.yml`)
- **[apple-ads-platform-api-swift](https://github.com/apple/apple-ads-platform-api-swift)** (`AppleAdsClient`, 1.109.0+, traits off) — Apple's generated client for the Apple Ads Platform API, used by the `ads` commands. It requires macOS 15 and swift-tools 6.2 and brings AsyncHTTPClient/NIO (its token fetch always uses them); the stripped release binary grew from 42.8 MB (0.23.1) to 64.4 MB (0.24.0, which also generates more ASCKit paths). Apple publishes no raw spec, so it can't be path-filtered like ASCKit; copying its generated `Client.swift`/`Types.swift` into an own target would drop NIO without changing command code.

## Authentication

Config file at `~/.ascelerate/config.json`:
```json
{
    "keyId": "KEY_ID",
    "issuerId": "ISSUER_ID",
    "privateKeyPath": "/Users/.../.ascelerate/AuthKey_XXXXXXXXXX.p8",
    "vendorNumber": "80012345",
    "ads": {
        "clientId": "SEARCHADS.…", "teamId": "SEARCHADS.…", "keyId": "…",
        "privateKeyPath": "/Users/.../.ascelerate/ads-private-key.pem",
        "adAccountId": 123456
    }
}
```

- `ads` is **optional** — only the `ads` commands use it; `ads configure` writes it (generating the P-256 key pair) and `configure` keeps it when rewriting the file.

- `configure` command copies the .p8 file into `~/.ascelerate/` and writes the config
- `vendorNumber` is **optional** — only the `reports sales`/`reports finance` commands use it (App Store Connect → Payments and Financial Reports). `configure` prompts for it (skippable); `--vendor-number` overrides per-invocation. Resolved by `Reports.resolveVendorNumber()`.
- **A key for one run:** `ASCELERATE_KEY_ID`, `ASCELERATE_ISSUER_ID` and `ASCELERATE_PRIVATE_KEY_PATH` (all three, or the run fails naming the missing ones) take precedence over `config.json` without changing it (`APICredentials` in Config.swift; the API client, `altool` and `configure --show` use it). With them, `builds archive` and the export also pass `-authenticationKeyPath`/`-authenticationKeyID`/`-authenticationKeyIssuerID` to `xcodebuild`, which provisions with the key instead of Xcode's Apple ID accounts; the configured key isn't passed, so provisioning without the variables is as before. Verified 2026-10-23: archive and export of a manually signed app with a key from the environment.
- File permissions set to 700 (dir) and 600 (files) — owner-only access
- JWT tokens use ES256 (P256, CryptoKit) signing with a 20-minute expiry; ASCKit's `TokenStore` reuses a token until its last minute
- The private key is read as PEM text from `privateKeyPath`

## Key Patterns

### AscelerateCore
- **What:** App Store Connect logic the commands share, in its own target with no terminal I/O: no ArgumentParser, no `print`/`readLine`, no reads of `autoConfirm`/`jsonMode`/`dryRunFlag`. The `ascelerate` target keeps parsing, prompts, colours, aliases, tables and JSON rendering, and calls into the core. Moved so far: the app/version lookups, `ProductVersions`, `createVersion` (used by `apps create-version`), `VersionLocalizations` (used by `apps localizations update/import`), the read side of `AssetLibrary` and `LocalizationMedia` plus `AssetLibrary.place` and the library listings (the CLI extends both types with checks, uploads and placement removal; unused assets are deleted in the core) plus `AssetLibrary.screenshotSpecs` and `previewSpecs` (accepted screenshot sizes and app preview sizes, lengths and frame rates per display type, live from `appAssetLibraryRefData`) and `previewType(of:)` (a display type's preview type, used by `media upload`), `deleteVersion`, the asset upload protocol and `ClassicMedia`, `AppInfos` (used by `app-info` and `age-rating`), `LicenseAgreements` (used by `apps eula`), `AccessibilityDeclarations` (used by `apps accessibility`), `CustomerReviews` (used by `reviews`), `AppEvents` (used by `events`), `CustomProductPages` (used by `product-pages`), `Experiments` (used by `experiments`), `Nominations` (used by `nominations`) and `ReviewSubmissions`, `Preflight` (used by `apps review preflight`) and `Releases` (used by `apps phased-release` and `apps release`), `ReviewAttachments` (used by `apps review attachment`), `PromotedPurchases` (used by `iap promoted`), `OfferCodes` (used by `iap offer-code` and `sub offer-code`), the promotional offer part of `Subscriptions` (used by `sub promo-offer`), `RoutingCoverage` (used by `apps routing-coverage`) and `EncryptionDeclarations` (used by `apps encryption`), `BuildUploadRecords` (used by `builds uploads` and the API upload's stray-record cleanup) and `MediaDownload` (used by `apps media download`), `InAppPurchases` (used by `iap`, except offer codes and pricing commands, which use its schedule calls) and `Subscriptions` (used by `sub`, introductory offers included, and by `apps subscription-grace-period`/`streamlined-purchasing`, except offer codes, promotional offers and the pricing commands), `Builds` (used by `testflight builds/versions/expire/notify/auto-notify/status/whats-new`, the TestFlight commands' `--build` lookup, `apps build attach/attach-latest/detach` and `builds await-processing`), `BetaGroups` and `BetaTesters` (used by `testflight groups info/create/update/delete/add-build/remove-build` and `testflight testers`; `testers import` now reads files with Windows line endings, which 0.25.3 read as one line), `TestInformation`, `ReviewInformation` and `BetaReview` (used by `testflight app-info/review-info/eula/status` and `apps review info`), `BetaFeedback` (used by `testflight feedback`) and `RecruitmentCriteria` (used by `testflight groups criteria`), `Certificates` (used by `certs` and the profile commands' certificate lookups), `BundleIDs` (used by `bundle-ids` and `profiles create`'s bundle ID lookup), `Profiles` and `Devices` (used by `profiles`, `devices` and the profile regeneration of `bundle-ids`), and the pure formatting and retry helpers; the rest moves one area at a time.
- **Rules:** a lookup that can be ambiguous takes a `choose: Choose<T>` closure (`findVersion`); the CLI wrapper of the same name passes `promptSelection` with its `--yes`/`--json` hint. Alias resolution stays in the CLI (`findApp(bundleID:)` → `resolveAlias` → `findApp(exactBundleID:)`). Errors are `LocalizedError`s, not `ValidationError`. Everything the commands use is `public`.
- **Moving code:** move it unchanged first, then adapt; verify with `Scripts/compare-with-release.sh` against the released binary (identical output and exit codes) plus `swift test`. A CLI file needs `import AscelerateCore` only when it uses a core symbol; the Ads files can import it (it doesn't re-export ASCKit).

### ASCKit (the App Store Connect client)
- **What:** every command talks to App Store Connect through ASCKit, a client generated by swift-openapi-generator from Apple's own OpenAPI spec. It replaced asc-swift in October 2026 (0.22.0): asc-swift lagged the spec (4.4.1 when Apple shipped 4.5.1), its closed enums failed whole responses on values Apple added later (screenshot display type `APP_IPHONE_DUO`, capability `ENHANCED_SECURITY`, a legacy encryption declaration's lowercase platform `ios`), its 2,508 generated files made release builds slow, and it decoded dates without their UTC offset, so every date it printed was 7-8 hours early.
- **Layout:** `Sources/ASCKit/openapi.json` is Apple's spec run through `Scripts/prepare-asc-spec.swift` (schema string enums opened to plain `String` so unknown values like placement state `ACTIVE` can't break decoding; query-parameter enums stay typed; bracketed parameter names get readable Swift names via the generated `nameOverrides` section of `openapi-generator-config.yaml`, e.g. `filter[bundleId]` → `filterBundleId`). The build plugin generates only the paths listed under `filter.paths` in that config. `ASCKit.swift` is hand-written: `Client.appStoreConnect(credentials:)` with JWT (cached token), `ErrorMiddleware` (every 4xx/5xx thrown as `ASCError` with Apple's entries and the `X-Rate-Limit` header; `ASCError.from(_:)` unwraps the runtime's `ClientError`), `ASCPaging.allPages` (Apple pages via a full `links.next` URL the spec doesn't model; a task-local swaps the request path for it, so any list operation pages; `ASCPaging.allPagesConcurrently` fetches the pages after the first a few at a time when the `next` cursor is `offset:total`, as the asset library's lists name theirs, and follows `next` one by one otherwise), and a date transcoder that accepts fractional and plain seconds.
- **Adding a command:** add the endpoint paths to `filter.paths` in `openapi-generator-config.yaml` (the build plugin only generates listed paths; a new path costs a ~70 s regeneration), get a client with `ClientFactory.makeClient()`, and call the generated operation: `try await client.appsGetCollection(query: .init(filterBundleId: [id])).ok.body.json`, `.created.body.json` for a POST, `.noContent` for a DELETE. Request inits take their arguments in the spec's alphabetical order with `_type` last (`.init(attributes:, id:, _type:)`), and every relationship needs its `_type` (`.init(id: app.id, _type: "apps")`).
- **Dry run (`--dry-run` or `ASCELERATE_DRY_RUN=1`):** `--dry-run` is taken out of the command line before parsing (`extractDryRunFlag` in `main()` and per workflow step, where it applies to that step only; ArgumentParser has no global options) and sets `dryRunFlag`; `ClientFactory.isDryRun` combines it with the environment variable. Reads go out as usual, but every POST/PATCH/PUT/DELETE is stopped before it leaves the machine: the method, path and pretty JSON body are printed to stderr and `ASCDryRunStop` is thrown (rendered as "Dry run: … was not sent."). Use it to verify a write command end to end against live data up to its first write. Presigned asset uploads go through plain URLSession, but always after a reserve POST, which the gate stops. `builds upload` (altool, outside the gate) skips the upload and records no build number under dry run. `run-workflow` continues past a step that failed because of stopped writes (`ASCDryRun.blockedWrites` grew during it), so one dry run shows every step's writes; a real error still stops it. `unlessDryRunStopped { … }` turns a stopped write into nil so a multi-step command goes on: `media upload` counts stopped files as "not sent", deletes for `--replace` as done, and uses placeholder IDs (`DRY-RUN-SET`, `DRY-RUN-IMAGE`) to preview later requests, ending with "Dry run complete. N files would be uploaded". A command with no confirmation prompt (`apps localizations update`, `apps create-version`, `apps phased-release --enable/--pause/--resume`) writes as soon as it runs, so only ever try those under dry run.
- **Enum catalog (`ASCEnums.swift`, generated):** the generated client carries every schema enum as a plain `String`, so the prepare script also writes `ASCEnum.<Name>`: one `String, CaseIterable` enum per named string enum schema (`ASCEnum.BundleIdPlatform`) and per inline enum in a `*CreateRequest`/`*UpdateRequest`/`*InlineCreate` schema, named after its path (`DeviceUpdateRequest` → status: `ASCEnum.DeviceUpdateRequestStatus`). Write commands validate input with `parseEnum(value, name:) as ASCEnum.X` and send `.rawValue`; case names are lowerCamel (`FREE_TRIAL` → `freeTrial`, keywords escaped). Display raw values with `formatState(raw)`, never by interpolating the enum.
- **Hourly API limit (`ASCRateLimitWait`, `RateLimitWaitMiddleware`):** a 429 carries `Retry-After` in seconds (seen live: 2,186 with `X-Rate-Limit: user-hour-lim:3600;user-hour-rem:-1;`; the window is rolling, a full quota was back about 40 minutes later). The middleware, inside the error middleware and outside JWT signing, waits that long and sends the request again; concurrent requests share one `RateLimitGate` (no request goes out while a wait is pending) and one notice, re-announced only when the wait grows by a minute or more. `ClientFactory` passes the notice (`RateLimitNotice`: stderr, a live countdown on a terminal, one line otherwise) and the cap: `ASCELERATE_MAX_RATE_LIMIT_WAIT` seconds in total per process (`0` returns the first 429), after which the 429 surfaces as before. `isTransientError` no longer retries 429 (a 429 that gets out means waiting was capped), and `rate-limit` builds its client with `waitsForRateLimit: false`. Bodies that can't be replayed (`iterationBehavior == .single`) are not retried. Tested with a fake server in `Tests/ASCKitTests` (`swift test`): wait-then-send, cap 0, cap across the run, four concurrent 429s with one notice.
- **Burst limit and pacing:** besides the hourly quota, App Store Connect refuses bursts: a 429 "The request rate limit has been reached" while the key still had about 3,400 of its 3,600 hourly requests left (seen 2026-10-22, reading price tiers four territories at a time, each paging at 200). Not every endpoint counts (seen 2026-10-22): the subscription endpoints (`subscriptions/…`, `subscriptionPricePoints/…`, `subscriptionPrices` POSTs, accepted or refused) send no `X-Rate-Limit` header and leave the hour's count as it is, while app, in-app purchase and territory requests and other writes (a PATCH of an app) count; the age rating endpoints (`appInfos/{id}/ageRatingDeclaration`, `territoryAgeRatings`) report a count of their own (3,595 left next to 3,209 for the rest), so a client showing the quota should skip theirs. `rateLimitObserver` gets the operation ID for that. `ASCRateLimitWait.maxWait` caps a single wait (a refused burst asks for seconds, a spent quota for most of an hour; a longer one returns the 429), and the client option `pacing: ASCRequestPacing(burst:perSecond:)` spaces requests with a token bucket shared by the process (`PacingMiddleware`, inside the wait so resent requests are paced too; tested). The CLI uses neither yet. Price tiers: `InAppPurchases.pricePoints(purchaseID:territoryIDs:)` and `Subscriptions.pricePoints(subscriptionID:territoryIDs:)` read up to nine territories per request (`limit` 8000, about 800 tiers each), and `PriceFile.resolve(batchSize:tiers:equalizations:progress:)` reads them in batches, reporting territories done.
- **Associated errors:** a 409 like "appStoreVersions … is not in valid state. This resource cannot be reviewed, please check associated errors" carries the real reasons in `errors[].meta.associatedErrors` (keyed by resource path). `ASCError.Entry.associatedErrors`/`reasons` decode them and both error formats print them as indented lines (tested in `ErrorDecodingTests`). Seen live 2026-10-09: `STATE_ERROR.ASSET_IN_POST_PROCESSING.APP_SCREENSHOT` "Asset is being processed" from a classic iPad screenshot whose library placement stayed PENDING for 17 hours while the screenshot read COMPLETE.
- **Explicit nulls (`ASCNulls.sending`):** generated request types omit nil properties, but Apple clears some values only when sent as JSON `null` (an event's `badge`, an intro offer's `endDate`, a version's build relationship `{"data": null}`). `try await ASCNulls.sending([["data", "attributes", "badge"]]) { try await client.appEventsUpdateInstance(...) }` runs the generated operation with those key paths of its JSON body set to null (`NullsMiddleware`, before the dry-run gate, so dry runs print the patched body).
- **Missing related objects:** a to-one GET answers "nothing related" with HTTP 404 or `{"data": null}` (which fails decoding the spec's non-optional `data`); `optionalRelated { … }` maps both to nil, and `ASCError.isMissingRelated(_:)` matches them in a `catch`.
- **Errors:** every 4xx/5xx becomes an `ASCError` (status, Apple's error entries with their `code`, title and detail, the `X-Rate-Limit` values); `ASCError.from(_:)` unwraps it from the runtime's `ClientError`. Transport and decoding failures stay wrapped in `ClientError`, whose description dumps the whole operation, so `ascUnderlyingError(_:)` unwraps them for `describeError` and the central formatter (URLError messages, unexpected-response errors).
- **Enum display:** raw values go through `formatFieldName`'s SCREAMING_SNAKE branch, which has a word map for non-Title-Case words (`ID`, `iOS`, `tvOS`, `iPad`, `iPhone`, `iMessage`, `iCloud`, `TV`, `URL`, `NFC`, `RSA`, `PSP`) plus whole-value overrides such as `VISION` → "Apple Vision". Always format the raw value (`formatState(platform.rawValue)`), never an interpolated enum: a case name such as `macOs` renders as "Mac Os". `Platform` (`--platform`) is a typealias of `ASCEnum.Platform`.
- **Generated names:** generated `included` cases are named after the resource `type` (`.preReleaseVersions`, `.customerReviewResponses`), not the schema; attribute names follow the spec (`bundleId`, `productId`, `familySharable`, `expired`, `supportUrl`), and opened enums are `String`, so compare states against raw values. `ASCError.isMissingRelated(_:)` covers Apple's two "no related object" answers (HTTP 404, or `{"data": null}` failing to decode). `X-Rate-Limit` isn't in the spec: wrap a call in `ASCRateLimit.header(of:)` to read it. The prepare script also drops empty parameter enums (`fields[appKeywords]`), which would generate an uncompilable enum with no cases.
- **Updating the spec:** `swift Scripts/prepare-asc-spec.swift ~/Downloads/openapi.oas.json` (rewrites `openapi.json` and the `nameOverrides` section; the path list is kept).
- **Only success responses are generated:** the prepare script drops every operation's 4xx/5xx responses (7,037 in 4.5.1). `ErrorMiddleware` throws those as `ASCError` before the generated client decodes them, so their typed cases were never used, and they were most of the generated code: dropping them took the client from about 344,000 to 180,000 lines and a release build of ASCKit from 25.6 GB of compiler memory to 16.6 GB (measured 2026-10-21; at `-Onone` 8.8 GB). Homebrew's CI machine ran out of memory on the full client.
- **Warnings and deprecations:** the ASCKit target builds with `-suppress-warnings` (an `unsafeFlags` setting, fine for a root package): the generated client references every attribute, parameter and schema Apple marks deprecated from its own Codable and query code, which buried real warnings under dozens of Apple's. Deprecation warnings are reported where an API is used, so a command using a deprecated endpoint or attribute still warns in the ascelerate target; replace it rather than silencing it there. Done so far: `sub availability` reads and edits the subscription's `UPFRONT` plan availability (`subscriptions/{id}/planAvailabilities`; Apple's plan availability IDs are base64 `{"a":"<subscription id>","p":"0"}`, and the upfront plan holds what the deprecated `subscriptionAvailabilities` did, verified live 2026-10-07), PATCHing it when present and POSTing one otherwise. `--plan monthly` does the same for the `MONTHLY` plan (Apple's "Monthly with 12-Month Commitment" billing of an annual subscription, under the same product ID; not offered in the USA and Singapore, which Apple rejects, so ascelerate doesn't check it); a subscription without one isn't offered that way. Age rating export/import keeps the `ageRatingOverride` JSON key but reads and writes `ageRatingOverrideV2` (EIGHTEEN_PLUS replaced SEVENTEEN_PLUS, which now fails validation with the valid values listed).
- **Verification record (October 2026):** every read command was compared with the asc-swift release (0.21.0) through `Scripts/compare-with-release.sh` (identical apart from the corrected dates and display fixes such as "I OS App Development" → "iOS App Development"), and every write command was run under dry run against live data with its request body checked, plus compared with 0.21.0 up to its confirmation prompt by piping `n` in. Writes that dry run could not reach for lack of live data, compiled and read only: phased-release pause/resume/complete/disable, `apps release`, `iap submit`, promoted remove/toggle/reorder, offer-code toggle/codes on existing codes, intro-offer update/delete, preview reserve, `media verify`'s retry, events update/delete/localizations/media (verified live since, 2026-10-21) and the analytics download chain (no report request).

### Adding a new subcommand
1. Add the command struct inside `AppsCommand` (or create a new command group)
2. Use `AsyncParsableCommand` for commands that call the API
3. Register in the appropriate `CommandGroup` in the parent's configuration (see below)
4. Use `findApp(bundleID:client:)` to resolve bundle ID or alias to app ID (CLI wrapper of the core's `findApp(exactBundleID:client:)`)
5. Use `findVersion(appID:versionString:platform:client:)` to resolve version (nil = prefers editable, prompts if multiple platforms; CLI wrapper passing `promptSelection` as the core's `choose`); version-scoped commands should add `@OptionGroup var platformOption: PlatformOption` and pass `platform: try platformOption.parsed()`
6. Use shared helpers: `formatDate()`, `formatState()` for enum display (AscelerateCore), `expandPath()`, color helpers (`green()`, `red()`, `yellow()`, `bold()`)
7. Run `ascelerate install-completions` to regenerate completions after adding commands

### Subcommand grouping
`AppsCommand` uses `CommandGroup` (swift-argument-parser 1.7+) to organize subcommands into sections in `--help` output:
- **ungrouped** (`subcommands:`): list, info, versions — general browse commands
- **Version**: create-version, copyright, build (attach, attach-latest, detach), phased-release, routing-coverage
- **Info & Content**: app-info (view, update, import, export, age-rating (view, export, import)), localizations (view, update, import, export), media (upload, download, verify)
- **Configuration**: availability, encryption, eula
- **Review**: review (preflight, status, submit, resolve-issues, cancel-submission, info, attachment)

When adding a new subcommand, place it in the appropriate `CommandGroup` or create a new one. Shell completions are alphabetically sorted by zsh — don't try to force custom ordering there.

### App aliases
- Aliases map short names to bundle IDs, stored in `~/.ascelerate/aliases.json`
- `resolveAlias()` in `Aliases.swift` is the single resolution function — if input contains no dots, look up in aliases
- `findApp()` in `AppsCommand.swift` calls `resolveAlias()` at the top — this covers all app, IAP, subscription, and build commands automatically
- Alias names must match `^[a-zA-Z0-9_-]+$` — no dots (dots distinguish real bundle IDs from aliases)
- `bundle-ids`, `profiles`, `devices`, `certs` commands do NOT resolve aliases (different domain)

### Version management
- **No `version:` on `CommandConfiguration`** — intentionally omitted. ArgumentParser leaks a root `--version` flag into every subcommand's completion function, which conflicts with subcommands that define their own `--version` option (e.g. `builds list --version`, `apps review status --version`).
- Version is stored as `static let appVersion` in `ASC.swift`.
- `ascelerate version` subcommand prints just the version number. `--version` and `-v` are intercepted in `main()` before ArgumentParser and produce the same output.
- `install-completions` stamps `# ascelerate vX.Y.Z` into completion scripts (after `#compdef` line for zsh) and `install-skill` stamps `<!-- ascelerate vX.Y.Z -->` into each installed skill file (across all targeted agents). The update-check (`skillVersionDetail()`) scans every installed agent path and only flags **stamped** skills (npx-installed ones are unstamped and skipped, so they don't false-positive). `install-skill` targets agents that are detected (`~/.claude` or `~/.grok` for the shared Claude Code/Grok Build entry, `~/.cursor`, `~/.windsurf`) or already have the skill; `--all` forces all four entries (incl. Copilot, which has no detectable dir). Grok Build reads the Claude Code skill path natively, so both share one entry/target file.
- `checkForUpdates()` (non-interactive, API commands) and `checkForUpdatesInteractively()` (bare invocation) detect outdated completions and/or skill, offering a single Y/n prompt or NOTE line. The version compare uses `isVersionOlder()` (numeric, component-wise) and only flags a stamp that is **strictly older** than the running binary — so an older `ascelerate` earlier in PATH never offers to *downgrade* completions/skill that a newer build installed.
- Both `install-skill` and the npx installer (`npx ascelerate-skill`) fetch `SKILL.md` from GitHub — the skill content is NOT embedded in the binary. `skills/ascelerate/SKILL.md` in the repo is the single source of truth.

### Shell completions (`install-completions`)
- ArgumentParser's generated completion scripts need post-processing:
  - **`#compdef` must be line 1** in zsh completion files — never prepend content before it or compinit won't recognize the file.
  - `patchZshHelpCompletions` / `patchBashHelpCompletions` — fix `ascelerate help <tab>` to list subcommands (ArgumentParser generates a broken/empty help function).
  - `-V` flag removed from all `_describe` calls so zsh sorts completions alphabetically.
- **Argument-level completions** via ArgumentParser's `completion:` parameter:
  - `.file(extensions:)` — file path completion filtered by extension (e.g. `.json`, `.workflow`, `.ipa`)
  - `.shellCommand()` — dynamic completions from a shell command (used for alias names from `~/.ascelerate/aliases.json`)
  - Bundle ID arguments use `.shellCommand("grep ...")` to extract alias keys from the aliases JSON file
  - File arguments use `.file(extensions: ["json"])`, `.file(extensions: ["workflow", "txt"])`, etc.

### Interactive mode
- Most provisioning commands (devices, certs, bundle-ids, profiles) support interactive mode — arguments and options are optional.
- When omitted, commands prompt with numbered lists fetched from the API (e.g. bundle ID picker, certificate picker, profile type selection).
- Text inputs use a recursive `promptText()` that retries on empty input, throws on stdin EOF, and throws under `--yes` (interactive input can't be auto-confirmed).
- `promptSelection`/`promptMultiSelection` refuse under `--yes` instead of auto-picking; `promptSelection` takes a `nonInteractiveHint` (e.g. "Pass --platform to disambiguate.") shown in that error.
- Selection lists use `[\(i + 1)]` numbering, `readLine()` input, `Int()` parsing, and range validation.
- `--yes` / `autoConfirm` is incompatible with interactive mode — commands throw `ValidationError` when required options are missing with `--yes`.
- `enable-capability` filters the type picker to exclude already-enabled capabilities; `disable-capability` only shows enabled ones.
- `enable-capability` and `disable-capability` offer to regenerate provisioning profiles after changes (delete + recreate with same settings) via `regenerateProfilesIfNeeded()` helper in BundleIDsCommand.swift.

### JSON output (`--json`)
- Read commands can offer machine-readable output via the shared `JSONOption` option group (Formatting.swift): add `@OptionGroup var jsonOption: JSONOption`, call `jsonOption.activate()` at the top of `run()`.
- Pattern: build a private `Encodable` result struct FIRST (fetch everything, no printing), then branch — `if jsonOption.json { try printJSON(result); return }` — and render the text/table output from the same struct. One data assembly, two renderers.
- JSON conventions (LOCKED — the skill/docs advertise this shape, don't break it): list commands emit a bare top-level ARRAY of objects; detail commands emit a single top-level OBJECT. Every object representing an API resource carries its `id`. Raw API enum values (`WAITING_FOR_REVIEW`, `IOS`), ISO 8601 dates (`Date` fields + `printJSON`'s `.iso8601` strategy), sorted keys, `nil` fields omitted (synthesized `Encodable`), empty results emit `[]` — never prose like "No reviews found." Warnings the text UI prints as prose become explicit booleans (e.g. `hasPricing`).
- Text rendering from raw values: `formatFieldName` handles single all-caps words ("MANUAL" → "Manual") and has raw-value overrides for platforms ("IOS" → "iOS", "MAC_OS" → "macOS", …) — so `formatState(rawString)` renders the same as the old enum-based path.
- `--json` implies non-interactive: it sets the global `jsonMode` (mirror of `autoConfirm`); `promptText`/`promptSelection`/`promptMultiSelection` refuse with the `--json` flag named in the error. `run-workflow` restores `jsonMode` after each step like `autoConfirm`. Errors go to stderr (central handler), so stdout stays parseable.
- Currently on: `apps list/info/versions`, `apps review preflight/status`, `builds list`, `reviews list/info` (list includes full review bodies + developer responses, saving per-review `info` calls), `testflight builds/status`, `rate-limit`, `iap list/info`, `sub groups/list/info`, `iap pricing show`, `sub pricing show`. Fan out to other read commands using the same pattern; `--json` is not for write commands.
- `apps review preflight --json` emits `{versionID, version, platform, state, passed, checks: [{group?, name, passed, detail}]}` — `group` is nil for top-level checks, a locale code for per-locale checks, or the `inAppPurchases`/`subscriptions` sentinels; the text table (group headers, indentation) is rendered FROM this model, and the exit code stays non-zero on failures in both modes (CI gate). Progress messages ("Checking build...") are suppressed under `--json`. A product in `DEVELOPER_REMOVED_FROM_SALE` is a deliberate choice: its check is `passed: true` plus `skipped: true` (omitted otherwise), shown as a yellow – and counted as skipped in the result line; neither its state nor its prices are evaluated.
- `pricing show --json` is the rich per-territory view (price + currency + start date/preserved for subs) and deliberately does NOT mirror the `pricing export` JSON — export/import keep their own import-compatible format.
- Shared entry structs: `CustomerReviewsCommand.ReviewEntry` (list element + info object), `SubCommand.SubEntry` (sub groups nests it, sub list flattens it with a `group` ref). `ResolvedBuild` (TestFlightCommand) carries raw `platform`/`version` and derives the display `train`/`label` from them.

### Output formatting
- **ANSI colors** — `red()`, `green()`, `yellow()` (orange 208), `bold()` in Formatting.swift. Auto-disabled when stdout is not a terminal (`isatty` check). `stderrRed()` uses a separate `isStderrTerminal` check for error messages.
- **Colored output conventions** — `green()` for success verbs ("Created", "Updated", "Deleted", etc.), `yellow()` for "Cancelled.", `stderrRed("Error:")` in central error handler. `red()` for failure indicators (e.g. preflight ✗).
- **`formatFieldName()`** — converts camelCase (`whatsNew` → "What's New") and SCREAMING_SNAKE_CASE (`PREPARE_FOR_SUBMISSION` → "Prepare for Submission"; short words such as for/from/in stay lowercase unless first) to human-readable titles. Has override map for special cases (URL suffixes, OS names, `CANCELED` → "Cancelled").
- **`formatState()`** — generic wrapper: `formatFieldName("\(value)")`. Use for any enum/state value displayed to the user (e.g. `.map { formatState($0) }`). Applied globally across all command files for platform, status, type, and state fields.
- **`localeName()`** — resolves locale codes to human-readable names via `Locale.current.localizedString(forIdentifier:)` (e.g. `en-US` → `en-US (English (United States))`). Applied to all locale display across commands.
- **`parseEnum()`** — validates a string against a `RawRepresentable & CaseIterable` enum, returning the matched case or throwing `ValidationError` with valid values list. Use instead of inline `guard let X = T(rawValue: .uppercased())` blocks. `parseFilter()` wraps `parseEnum()` for optional API filter values (returns `[T]?`).
- **`fetchAll()`** — flattens already-fetched pages (`ASCPaging.allPages`) into a single array with an empty guard and optional sort. Used by `promptDevice()`, `promptCertificate()`, `promptBundleID()`, `promptProfile()`.
- **`resolveFile()`** — resolves a file path from an optional argument; lists matching files by extension in the current directory as a numbered picker, with manual path entry fallback. Used by `localizations import` and `app-info import`.
- **ANSI-aware Table** — `Table.print` uses `visibleLength()` (strips ANSI codes via regex) and `padToVisible()` for correct column alignment when cells contain colored text. All-empty rows (`["", ""]`) render as blank lines for visual grouping.

### Error handling
- `ASCClient.main()` overrides the default entry point to catch and format errors centrally.
- `ASCError`: rate limit (429, with the hourly limit and remaining requests), HTTP status codes (401/403/5xx) and Apple's error entries.
- `URLError` (unwrapped from the runtime's `ClientError` by `ascUnderlyingError`): connectivity issues (no internet, DNS, timeout, connection lost, TLS). Other wrapped failures print their underlying error, never the `ClientError` dump.
- `ASCDryRunStop`: a write blocked by `ASCELERATE_DRY_RUN=1`.

### Workflow files (used by run-workflow)
- One command per line, without the `ascelerate` prefix
- Lines starting with `#` are comments, blank lines are ignored
- Quoted strings are respected for arguments with spaces (e.g. `--file "path with spaces.json"`)
- Without `--yes`: prompts once to confirm the workflow, then individual commands still prompt normally
- With `--yes`: sets `autoConfirm = true` globally, all prompts are skipped
- `autoConfirm` is restored after each step — a single step with `-y` (or a nested `run-workflow --yes`) must not auto-accept prompts in later steps of a non-`--yes` workflow
- Commands are dispatched via `ASCClient.parseAsRoot(args)` — any registered subcommand works
- Nested workflows supported (`run-workflow` can call another workflow file) with circular reference detection via `activeWorkflows` path stack
- `builds upload` records the uploaded build number **per platform** (`recordUploadedBuild`/`lastUploadedBuild(for:)` in Formatting.swift) — subsequent `await-processing` (via its `--platform`) and `build attach-latest` (via the target version's platform) target the just-uploaded build for the RIGHT platform, avoiding both API propagation races and cross-platform build-number mixups when one workflow uploads iOS and macOS. A platform-specific miss never falls back to another platform's number; only a platform-less lookup uses the most recent upload.

### Accessibility declarations (`apps accessibility`)
- One `accessibilityDeclarations` record per app and device family (`deviceFamily`: ASCEnum.DeviceFamily), nine `supports…` booleans (VoiceOver, Voice Control, Larger Text, Dark Interface, Differentiate Without Color Alone, Sufficient Contrast, Reduced Motion, Captions, Audio Descriptions; CLI names in `AccessibilityDeclarations.features`), a `state` (DRAFT, PUBLISHED, REPLACED) and a write-only `publish` flag on update. Publishing a changed declaration leaves the old one as REPLACED (`view` hides those unless `--all`). Some features don't apply to a family: App Store Connect doesn't ask about Larger Text on the Mac, whose declarations store no value for it (shown "-"), so `AccessibilityDeclarations.features(for:)` leaves it out, create/update don't send it, and `set` refuses it for `mac` (the other families' exceptions are unknown; no declarations to check). `set` sends the full declaration; `publish` PATCHes `publish: true` on every DRAFT.
- **Drafts (verified live 2026-10-20/21):** a family takes one draft at a time (another POST is refused as a duplicate); a draft can be edited and deleted, a published declaration only replaced (edit it by creating a draft); publishing needs the app on the App Store for that family's platform (refused otherwise). Live-verified: create, edit, delete and publish of drafts, including a Mac declaration without Larger Text (2026-10-21).

### Nominations (`nominations`)
- Featuring nominations for Apple's editors (`/v1/nominations`): type `APP_LAUNCH`/`APP_ENHANCEMENTS`/`NEW_CONTENT` (CLI: launch, enhancements, new-content), name, description, publish start (required), optional end date, device families, locales, notes, supplemental material URLs, pre-order; `relatedApps` (one or more apps) is required. `--territories` sets `supportedTerritories` plus `launchInSelectMarketsFirst`. `create` saves a draft unless `--submit`; `submit`/`archive` PATCH `submitted`/`archived: true`.
- **`filter[state]` is required on the list and takes a single value** (a comma list 400s with "Expect one of DRAFT,SUBMITTED,ARCHIVED"), so `list` queries each state.
- **An update must carry exactly one of `submitted` and `archived`** (without: 422 "At least one of parameters 'submitted or archived' is required"; both: "Not allowed to provide parameters 'submitted' and 'archived' together"; `archived: false` on a draft: "from [DRAFT] state to [UNKNOWN] state"). `Nominations.update` sends the one matching the current state (`archived: true` for an archived one, else `submitted` as it is), from `state:` or a read first; `nominations update` failed before this.
- **Other fields:** `locales` are the App Store's locale codes in uppercase (`EN-US`, `TR`, `ZH-HANS`; App Store Connect offers 50, `Nominations.locales`). `supportedTerritories` are the relevant countries or regions (none is valid); `launchInSelectMarketsFirst` and `preOrderEnabled` are App Store Connect's App Launch checkboxes (its form keeps them as they are when the type changes to another, which hides them); `hasInAppEvents` is "Do you intend to submit a new in-app event"; `notes` is "Helpful Details" (500 characters; name 60, description 1,000). A cleared `publishEndDate` (a day instead of a time frame) is sent as null. Sending only `supportedTerritories` keeps `relatedApps`. Actors come without `actorType` (only a name or an `apiKeyId`), which `ReviewSubmissions.Actor` infers.
- Live-verified 2026-10-21 on a test app's drafts: create, update of every field (related apps, platforms, territories, languages, launch flags, in-app event flag, notes, links, time frame and back to a day), delete. Submit and archive compiled only (a submission reaches Apple's editors).

### Product page optimization (`experiments`)
- v2 experiments (`apps/{id}/appStoreVersionExperimentsV2`, `/v2/appStoreVersionExperiments`; resource type `appStoreVersionExperiments`; the v1 endpoints are deprecated): name, platform, `trafficProportion` (percent of visitors who see a treatment), state, `reviewRequired`, start/end dates. Treatments (`appStoreVersionExperimentTreatments`, related through `appStoreVersionExperimentV2`, optional `appIconName`) hold one localization per locale (`appStoreVersionExperimentTreatmentLocalizations`), which owns classic screenshot/preview sets and library placements like a custom product page localization: `AssetLibrary.Owner.treatmentLocalization` (`ClassicMedia.Owner` is the same enum), and `LocalizationMedia` serves both `product-pages media` and `experiments media`. `media upload` creates the treatment localization after the confirmation when it's missing.

A new test's `reviewRequired` is true. Each new localization is a copy of the live version's: classic sets COMPLETE and library placements ACTIVE, matching the source (App Store Connect dims a size that falls back to a larger size's screenshots as "Using Existing Assets"). Creating a localization takes a few seconds while the media are copied. An alternate app icon to test comes from the live version's build (`builds/{id}/icons`, `Experiments.icons`; a build without alternates lists only its APP_STORE icon, masked and unmasked). Renaming a treatment, changing the traffic share, adding and deleting treatments and adding and removing languages were verified; an upload to a treatment left the live version's set unchanged.

### Reports (`reports sales` / `reports finance` / `reports analytics`)
- **Sales/Finance endpoints return a gzipped TSV body (`application/a-gzip`), NOT JSON.** On ASCKit the operation exposes it as `.ok.body.applicationAGzip`; `Reports.reportText()` collects it and decompresses it with the core's `Gzip.decompress` (it skips the gzip header and trailer and inflates the DEFLATE body with Foundation's zlib decompression, which doesn't read the header itself; no `gzip` process) → UTF-8 text. Analytics segments use the same. `SalesReports` (core) downloads a summary report (nil on 404) and reads its rows (product type → download, re-download, update, in-app purchase, subscription; units; proceeds per unit; an in-app purchase's app by its SKU in `Parent Identifier`). URLSession does NOT auto-decompress this content type.
- **Vendor number** is required for sales/finance (not analytics). Stored optionally in `config.json` (`vendorNumber`), overridable via `--vendor-number`, resolved by `Reports.resolveVendorNumber()`.
- **Sales report summary** groups `Units` by (Title, SKU, Product Type Identifier); `--bundle-id` filters rows by the `Apple Identifier` column (== app's numeric ID from `findApp`). `--raw`/`--output` emit the unparsed TSV. Default `--date` is the most recent completed period in Apple's reporting time zone (`Reports.defaultSalesDate`); weekly keys off the Sunday ending the week.
- **Finance report `--date` is a *fiscal* period** `YYYY-MM` (MM = Apple fiscal period 01–12, not a calendar month); `--region` is required. Summary sums `Quantity` by title and `Extended Partner Share` by currency, skipping footer/total lines (non-numeric `Quantity`).
- **A 404 from a download is surfaced via `Reports.notFoundHint()`** — the download path doesn't parse the JSON error body, so a bare "HTTP 404" is rewritten to "report not available yet / no activity; try an earlier date".
- **Analytics is async + multi-step**: find-or-create an `analyticsReportRequest` for the app (`apps/{id}/analyticsReportRequests` filtered by accessType; reuse one not `isStoppedDueToInactivity`, else POST — prompts first, never auto-creates without `-y`) → list `reports` by `--category` (picker if multiple, or `--report-name`) → list `instances` by `--granularity` (picks latest `processingDate`, or `--processing-date`) → page `segments` → download each segment's `attributes.url` (presigned, gzipped) via plain `URLSession`, gunzip, save one CSV per segment to `--output` dir. A freshly created snapshot has no instances yet — the command tells the user to re-run later.

### Apple Ads (`ads`, Apple Ads Platform API 1.0)
- **Which API:** the Apple Ads Platform API (`https://api.ads.apple.com/v1`, August 2026). The old Campaign Management API v5 is sunset on 2027-01-26; never build on it. Requests carry `X-AP-Context: adAccountId=<id>` (`Ads.context`); lookups are `POST …/query`; responses wrap data in `result`.
- **Client:** the API logic lives in the `AscelerateAds` target (no terminal I/O, like AscelerateCore): `Ads.withClient(credentials, options:) { client in … }` builds Apple's `AppleAdsClient` with a URLSession transport and `Ads.Middleware`, and unwraps failures (no `ClientError` dumps; auth and decoding errors become `AdsError`). `Ads.Options` carries a write gate and a rate limit notice; the CLI's `Ads.withClient(ads)` (an extension) reads the config's key file, passes the dry-run gate and stderr notice, and sets `AdsError.credentialsHint` to name `ads configure`. Core functions take the `X-AP-Context` value (`context:`); the CLI keeps overloads taking its `AdsConfig`. Moved so far: the client and middleware, AdsError, `/query` paging, the ad account (its time zone), campaigns, ad groups, keywords, negatives, report requests (days in the ad account's time zone by default, or UTC, which search term reports refuse) and paging, the campaign report (`campaignReportRows`, used by `reports campaigns`), bulk/decodeRaw, Amount and Metrics; lookups by name, prompts, Scope and the table rendering stay in the CLI. Verified 2026-10-26: read commands, reports and dry-run writes identical before and after the move. ASCKit and AppleAdsClient both generate top-level `Client`/`Components`/`Operations`, so **no file may import both**: App Store Connect lookups for ads live in `Ads/AdsASC.swift`.
- **Middleware:** reads (only) are retried twice after a timeout or dropped connection (seen live on appleid.apple.com and the API); the dry-run gate (reads are GETs, `/query` POSTs and `/search/…`; every other request is printed and stopped as ASCKit's `ASCDryRunStop`, via `adsDryRunStop`, so `--dry-run`, `unlessDryRunStopped` and run-workflow handle both APIs alike); error bodies `{"error":{code,message,details[{code,message,info.field}]}}` → `AdsError` (`message` is sometimes absent); 429 → waits `Retry-After`/`RateLimit-Reset` (4 attempts; the SDK has no rate-limit handling).
- **Spec vs API mismatches (verified live 2026-10-13):** every `/query` result is untyped (`OpenAPIObjectContainer`) — `Ads.query` pages it and decodes into Apple's own models with the API's date format (UTC, `yyyy-MM-dd'T'HH:mm:ss.SSS`, no zone). Bulk create/update responses can't decode (base `Response.result` typed as object, the API sends an array) and impression share sends `promotedObjectId` as a number — `Ads.decodeRaw` captures the raw body (task-local box in the middleware) and decodes it itself, dropping the generated `DecodingError`; `Ads.bulk` reads per-item `{correlationId, success, result, error}`. Keyword suggestions reject sorting by `popularity` despite the docs (sorted client-side). The generated client has no bulk-delete operations (single `DELETE /negative-keywords/{id}` is used).
- **Filter rules the API enforces:** report `campaignId` filters take only EQUALS for API users, and keyword/search-term reports require one → `Ads.perCampaign` (4 concurrent). The campaign report is one unfiltered request filtered client-side (`Scope.contains`). Negative keyword `/query` requires an `adGroupId` condition (IS_NULL for campaign-level, EQUALS per ad group). Impression share wants `promotedObjectId` IN. Recommendations/suggestions take `promotedObjectId` + `promotedObjectType: APPSTORE_APP`.
- **Reports:** totals are summed from the shown rows (`Metrics.total`, Apple's formulas, 4 decimals) so they always match the scope; averages Apple reports as 0 with nothing to divide by become nil. Both conversion rates are shown: `tapInstallRate` (CR Tap) and `totalInstallRate` (CR Total, includes view-through, can exceed 100%). Search terms require the ORTZ time zone (all reports use it). Table numbers use en_US grouping regardless of the user's locale.
- **Writes:** confirm first (`-y` skips), dry-run verified. Keyword/negative creation and keyword updates use the bulk endpoints with `allowPartialSuccess: true` (one request against the rate limit), reported per item. `--bid` is refused on Max Conversions campaigns. Amounts take the campaign's budget currency. Live-tested 2026-10-13 on a paused campaign: negatives add/remove, keyword pause/resume.
- **Campaign create:** POST /campaigns then POST /adgroups. Max Conversions "requires an automated ad group" (Apple) and the API doesn't add it: ascelerate creates "Automated" with `automatedKeywordsOptIn` + `automatedKeywordsRequired` true and pricing CPT, and **no `bidStrategy` and no `startTime`**: the API rejects both on it ("AdGroup cannot have a bid strategy", "Start time not allowed for automated keywords required Ad Groups"), although a web-created one reads back with a MAX_CONVERSIONS strategy. `ads adgroups create --campaign X --automated` adds it to an existing Max Conversions campaign. Live-verified 2026-10-13 (a Max Conversions campaign: campaign create, then the automated group after the fix). Manual: "<name> Ad Group" with MANUAL_CPT/TAP and `--default-bid`. `--like` copies the campaign's targeting (placement), billing event and `regulationResponses` (France's CAMPAIGN_SAPIN_LAW), and for manual its ad group's device targeting and Search Match. Created PAUSED by default; under dry run a placeholder campaign ID shows the ad group request. If the ad group POST fails the campaign stays (paused) and the error says so.
- **Campaign bid:** `bidStrategy.bid` is the per-auction ceiling for Max Conversions ("an upper bound"; for Manual CPT it governs participation). Apple requires `bidStrategyType` and `bidStrategyGoal` with every bid strategy update, so `campaigns bid` copies them from the campaign.
- **CPA goal:** the ad group `cpaCap` is deprecated in the Platform API (Apple: use `bidStrategy` with MAX_CONVERSIONS). ascelerate still shows it (`adgroups` "CPA Goal"), copies it on create and accepts `--cpa-goal`; whether Apple still applies it is undocumented.
- **Ad groups:** create needs `pricingModel` and should carry the source group's `bidStrategy`, `cpaCap` (CPA goal) and `targeting`; the create/update types mirror the read types, so `Ads.convert` re-encodes them as JSON (stays exact if Apple adds targeting fields). New groups default to PAUSED: an empty group with Search Match on spends at once. Update sends only the changed fields, except that a default-bid change also sends the group's current `bidStrategyType`/`bidStrategyGoal` (Apple requires them with any bid strategy update; live-verified 2026-10-13). Create requires `startTime` although the spec marks it optional (400 "Attribute [startTime] is required"); ascelerate sends now. Age targeting is `minAge`/`maxAge` `{include: ["18"]}` (18–64; no maxAge = 65+). Live-verified 2026-10-13: two paused age groups created and 32 keywords copied into each (`keywords copy`, bulk-create).
- **Opportunities:** `ads opportunities` aggregates a campaign's search term rows by term (one row per serving keyword/ad group), compares with its keywords and negatives (any match type), and classifies against the campaign's own CPI, tap CR and TTR (thresholds in the command's `discussion`). Hidden low-volume terms are skipped; terms already negative are skipped; a term that is one of the campaign's keywords is never a negative candidate. Brand searches (app name before ":"/" - " from App Store Connect, plus `--brand`) are excluded from the averages and from negatives: in one French campaign the brand's CPI 0.05 put the average at 0.14 and flagged the core term "bloqueur d'appel" as a negative; without brand rows the average is 0.23.
- **Max Conversions campaigns:** `opportunities` suggests only negatives there (Apple picks the searches; keyword suggestions don't apply). Apple accepts campaign-level negative keywords on them (live-verified 2026-10-13).
- **Recommendations:** apply/dismiss bodies are `[{id, promotedObjectId, promotedObjectType}]`; the commands look the IDs up among open (AVAILABLE) recommendations first. Apple reports expectations it has no estimate for as 0 (shown as "-").
- **Breakdowns (`reports campaigns --by`):** `groupBy` on the campaign report (keyword/search-term reports allow only device and country). Region/city need `countryCode` in `groupBy` too (Apple 400s otherwise; added automatically). Apple returns unknown values both as `UNKNOWN` and as a missing field in separate rows; `merged` sums them. Verified 2026-10-13 on four storefronts: age and region 100% unknown, gender over 99.5% (only users with Personalized Ads on are known); device is complete.
- **Ads and product pages:** creatives are account-level and reusable (`DEFAULT_PRODUCT_PAGE`/`CUSTOM_PRODUCT_PAGE`, destination `APP_STORE_PRODUCT_PAGE` with `parameters.adamId` + `productPageId`); an ad = ad group + creative, only one ENABLED per ad group (create with `--enabled` pauses the serving ones first). `/product-pages/query` is filtered by `adamId`; `/ads/query` by `campaignId`. Seen live 2026-10-13: none of the apps has custom product pages (both queries return nothing), and `/ads/query` doesn't return Apple's implicit "Default Ad" that `reports ads` shows, so whether an enabled custom-page ad must first pause that implicit ad is unverified. Ads create/pause/resume are dry-run verified only.
- **Change history (`ads history`):** POST /change-history/query needs an `eventTime` BETWEEN filter (yyyy-MM-ddTHH:mm:ss.SSS, `options.timeZone` ORTZ) **and an `entityType` filter** (400 "EntityType required" although the docs call it optional; ascelerate sends Campaign, AdGroup, Keyword, NegativeKeyword). With `options.metadata: latest`, each summary row's `metas` (untyped) carry `detailId` plus a `meta` object (text, matchType, bidAmount, campaignId, adGroupId, status); GET /change-history/{detailId} gives `details[].changes[]` {field, oldValues, newValues}, fetched for UPDATE events only, 4 at a time. Apple logs some bulk keyword updates and ad group default-bid changes as CREATE (verified live 2026-10-13), so creates show the resulting values from `meta`.
- **Target CPA suggestion:** POST /suggestions/target-cpas/query with promotedObjectId/promotedObjectType (+ countryOrRegion IN): the highest tap-install CPI across storefronts with ≥10 installs in 28 days.
- **Genres:** `keywords popularity --app` maps the app's primary App Store category to an Apple Ads genre (`Ads.genre(forCategory:)`; UTILITIES/PRODUCTIVITY → PRODUCTIVITY_UTILITIES); unmapped categories (weather, music, reference…) need `--genre`.
- **Live-verified writes:** negatives add/remove, keyword add, copy, pause/resume and bid, ad group create, update and resume, recommendation dismiss, campaign bid, budget and resume (2026-10-13). Dry-run only: campaign pause, ad group pause, recommendation apply.

### API calls
- **`filterBundleId` does prefix matching** — `com.foo.Bar` also matches `com.foo.BarPro`. Always use `findApp()` which filters for exact `bundleID` match from results.
- **Null data in non-optional response fields** — Several GET sub-resource endpoints return `{"data": null}` when no related object exists (e.g. build on version), others HTTP 404 (e.g. EULA on app); the generated response types have non-optional `data`. Wrap such fetches in `optionalRelated { … }`.
- Builds don't have `filterBundleId` — look up app first, then use `filterApp: [appID]`
- **In-app events (verified live 2026-10-21 on a test event, never submitted):** an event's media are asset library placements (`EVENT_CARD_ASSET`, `EVENT_DETAILS_PAGE_ASSET`, group `DEFAULT_PROFILE`, category `CREATIVE_ASSETS`): an `appEventScreenshots`/`appEventVideoClips` upload becomes a placement with the same ID, and a library image placed on an event localization (`AssetLibrary.Owner.eventLocalization`) lists as an `appEventScreenshot`. One image or video per localization and slot (a second is refused, 409); `DELETE appEventScreenshots/{id}` answers 500 for media placed from the library (although it deletes them), so `AppEvents.deleteMedia` deletes the placement (204 for both). Specs (`appAssetLibraryRefData`, now with aspect ratios for size ranges): card 16:9 1920×1080–3840×2160, details page 9:16 1080×1920–2160×3840, videos 15–30 s at 30 or 60 fps. A schedule needs at least one territory (409), so "all countries or regions" is all 175. `purchaseRequirement` is a free string; App Store Connect's two values are `NO_COST_ASSOCIATED` (Not Required) and `IN_APP_PURCHASE` (Required). `previewFrameTimeCode` is `hh:mm:ss:frame` (`00:00:03` is refused). Adding an event to review (a `reviewSubmissionItems` POST with `appEvent`; the 409's associated errors name what's missing) requires a badge and `primaryLocale` (empty until set) and processed media; it moves the event to READY_FOR_REVIEW, where only `territorySchedules` and `priority` can change (other fields and localizations: 409) and deleting is refused. Taking it out of the draft is a DELETE of the item, which returns the event to DRAFT.
- **Asset library paging (seen 2026-10-24):** the images and videos lists page with `cursor=<offset>:<total>` (e.g. `200:7225`), and a cursor made for any offset is accepted (a bare `1000` isn't), so `AssetLibrary.images`/`videos`/`assetsWithPlacementState` read the pages after the first four at a time: 7,225 images in 7.8 s instead of 19.7. A page of 200 images with `include=placements&limit[placements]=1` brings all 200 placements (the 50-included cap seen on builds doesn't apply). `assetsWithPlacementState` reports progress after each page (everything read so far, and the total).
- **Asset library pages (seen live 2026-10-21 in App Store Connect and the API):** an asset's Name is its `referenceName`, which starts as the file name and is numbered by App Store Connect when repeated ("01_hero.png (255)"); `rename`, `archive` (`archived: true`) and DELETE are the asset's own writes. App Store Connect offers Add for Review on an unplaced asset being prepared (a `reviewSubmissionItems` POST with `appAssetLibraryImage`/`appAssetLibraryVideo`, `ReviewSubmissions.add(.libraryImage)`), Delete on an unused one and Archive on one that went through review. What an asset works with comes from its `specId` (`specIDs(client:)` inverted; app screenshots also work as iMessage screenshots, `IMESSAGE_APP_SCREENSHOT` in groups named like the iPhone and iPad ones with an `IMESSAGE_` prefix). An image's placements list includes their owner localizations, but an included localization comes without its relationships (with or without `fields`), so `usage(of:)` reads each owner localization's parent on its own (version, custom product page version, treatment or event). Deleting an owner (a custom product page, a test, an event) leaves its placements behind, INACTIVE with every owner relationship null: App Store Connect says the asset "hasn't been used yet" and offers Add for Review and Delete, `usage(of:)` leaves them out, but the asset's DELETE still answers 409 `STATE_ERROR.ASSET_HAS_PLACEMENTS`, and a DELETE of such a placement answers 204 without removing it (seen 2026-10-21). App Store Connect's own Delete Asset fails on them too, so such an asset can't be deleted at all. Deleting a custom product page orphans every placement still on it, uploaded or copied from a template (seen 2026-10-21); media deleted from the page first leave no placement. So every core delete of a media owner (a version, page, test, treatment, event or one of their languages) first deletes the owner's placements (`AssetLibrary.clearPlacements`), on a page, test or event only while it's editable (one that went through review holds only reviewed images); the images stay in the library, unplaced and deletable. Verified 2026-10-21: a page with a classic screenshot and a header image, and an event with a card in two languages, deleted through the CLI left their images without placements. Deleting a classic screenshot (e.g. a treatment's, with `experiments media delete`) leaves its library image behind, unplaced; `media library --delete-unused` finds those.
- **Custom product pages (verified live 2026-10-21 on a test app's pages, none submitted):** an app takes 70. Creating needs an inline version and at least one inline localization even with a template (409 "You must provide a value for the relationship 'appCustomProductPageVersions'"); `appStoreVersionTemplate` takes any App Store version, `customProductPageTemplate` only a page with an approved version ("CUSTOMPRODUCTPAGETEMPLATE must have approved version"), and only the localizations sent are created (`CustomProductPages.create` takes `locales`). What a version template copies depends on its screenshots: copied from an approved live version (six languages, 17 screenshots each), every new localization's classic sets matched the source at once and its library placements followed over minutes, while the request itself answered 500 although the page was created (`CustomProductPages.create` then returns the page found by name). Copied from a version whose screenshot was new and unreviewed, the screenshot landed only as a library placement and the classic set listed none (still after 12 minutes; App Store Connect shows the placements), so `product-pages media list`, which reads classic sets, misses it; deleting the placements removed the set's classic screenshots too. `visible: false` is App Store Connect's Disable Link. Adding a page version to a draft submission (`ReviewSubmissions.add(.customProductPageVersion)`) locks its text and media (409 "Version … is not in modifiable state"); the page's name and visibility still change. Deleting the draft item returns it to PREPARE_FOR_SUBMISSION. Changing an approved page's text or media takes a new version (`CustomProductPages.createVersion`, App Store Connect's way); not verified live yet, since no approved page was available (2026-10-21). A submission item's included page version doesn't name its page, so `ReviewSubmissions.items` reads the version with its page included (one request per page item).
- **Customer reviews (verified live 2026-10-21):** the API has written reviews only; App Store Connect's ratings (stars without a review, their average and star breakdown) have no endpoint, and an app's written reviews average lower than its ratings (one app: 4.14 from 6,875 reviews, 4.5 from 72,004 ratings). `CustomerReviews.ratingCounts` counts reviews per star from each filtered list's `meta.paging.total` (five `limit=1` requests). A review has no version or platform: `appStoreVersions/{id}/customerReviews` lists one version's (same filters and sort). Without a `sort` the list isn't by date (2017 reviews first). `customerReviewSummarizations` requires `filter[platform]` and returned nothing for that app in the US, Türkiye and Germany. Reporting a concern has no API. A review takes one response: replacing it is delete, then create.
- **App price schedule and availability (verified live 2026-10-21 on a test app):** a schedule is a base territory plus manual prices (each with an optional start and end date; one starting later is a planned change) and Apple's automatic prices for the other territories; `POST appPriceSchedules` replaces it whole (inline `appPrices` with `${local-id}`s). A new app's schedule already names a base territory (USA) but has no prices: listing them answers 404 "no resource of type 'null'", which `AppPricing.schedule` reads as no price yet. Price tiers page at 200 at most (USA has 658); `appPricePoints/{id}/equalizations` gives a tier's price in the other 174 territories in one request. Prices currently applying are sent back without their start date and ended ones left out (`Schedule.newPrices`). Availability (`appAvailabilities` v2) is set up once with every territory inline; a second setup is refused ("already exists") and v2 has no update, so `availableInNewTerritories` can't be changed through the API afterwards (App Store Connect can). Territories change one at a time (`territoryAvailabilities` PATCH). A new app's territories read `CANNOT_SELL` plus `AVAILABLE_FOR_SALE_UNRELEASED_APP`; a territory taken off sale reads just `CANNOT_SELL`; the other statuses name why it can't be sold (age rating, Brazil tax ID, GRN, ICP number, trader status). Verified: first price, a dated price change and its removal, a manual price in one territory and its removal, availability setup and a territory change; ending pre-orders compiled only (no app with pre-orders). `apps availability` reads and updates through `AppAvailability`, `apps pricing` through `AppPricing` (verified live on a test app 2026-10-21: dated base price and its cancellation, override, keep, remove, a two-territory sale and its cancellation, export, and import matching one territory by equalization and one by its tiers).
- **In-app purchases (verified live 2026-10-21 on a test app's purchases, never submitted):** `InAppPurchases` serves the `iap` commands (output unchanged against 0.25.3, offer codes and promoted purchases still in the CLI). A purchase's price schedule has the app's shape, so it reads and writes `AppPricing.Schedule`/`NewPrice` and takes the same edits; the CLI's `iap pricing` still sends one start date for every price. Its tiers take `limit` up to 8000 (an app's take 200). App Store Connect limits a localization's display name to 35 characters and its description to 55, the reference name to 64 and review notes to 4,000. A new purchase has no availability of its own (it follows the app's; `iap availability --remove` then starts from an empty list, as before). `contentHosting` is often left out. A processed image or review screenshot is renamed `SOURCE`; before that its `imageAsset.templateUrl` comes back empty rather than missing (the core reads an empty one as none), and a promotional image took from 10 seconds to over a minute (seen 2026-10-22). Family Sharing can't be turned off once on. Adding a purchase to a draft submission is its pending version (`ReviewSubmissions.DraftItem.inAppPurchaseVersion`, from `ProductVersions.pendingIAP`); not verified live.
- **Subscriptions (verified live 2026-10-22 through the CLI on a test app's group, never submitted):** `Subscriptions` serves the `sub` commands (output and export files unchanged against 0.25.3; offers and the pricing commands' internals still in the CLI). Group create/rename/delete, group and subscription localizations (create, update), subscription create/update/delete, plan availability (created on first set), promotional image and review screenshot upload/delete all worked. A new subscription reads MISSING_METADATA with a pending v1 (PREPARE_FOR_SUBMISSION) until it has prices. A price needs the subscription's own plan availability first (without one every territory is refused with 409 "The provided territory is not supported for your subscription and planType"); once it exists, any territory takes a price, also one outside the availability. `prices` reads the UPFRONT plan only; `Prices.current` is what new subscribers pay in each territory (the latest started price), `planned` the ones starting later. A raise that keeps existing subscribers on their price marks the price before it `preserved` (seen live: TUR 999.99 preserved next to 1,019.99 planned for the next day), and new subscribers still pay that one until the raise starts. Limits: a group localization's name 35 and custom app name 30 characters. Adding a group or subscription to a draft submission goes through its pending version (`DraftItem.subscriptionGroupVersion`/`.subscriptionVersion`); not verified live.
- **Grace period and streamlined purchasing (verified live 2026-10-22 on a test app):** both are app-wide (App Store Connect shows them under the subscription groups). Every app has a `subscriptionGracePeriods` record (ID = app ID; off reads both opt-ins false with no duration or renewal type), changed only by PATCH. `optIn: true` alone turns sandbox on too with 16 days and all renewals; production on with sandbox off is refused (409 "cannot be enabled in prod and disabled in sandbox"); turning both off clears duration and renewal type, and edits while off are ignored. Sandbox on with only a duration left the renewal type empty, so send all four when turning it on. Streamlined purchasing is the app attribute `streamlinedPurchasingEnabled` (on by default); turning it off is refused unless the latest approved build uses the StoreKit `PurchaseIntent` API (409), so only turning it on was verified.
- **Introductory offers (verified live 2026-10-22 on a test app's subscription):** an offer is one `subscriptionIntroductoryOffers` record per territory: a POST without a territory is refused (409 "You must provide a value for the relationship 'territory'"), so the CLI's old "global" offer never worked. A PATCH of the subscription with the offers inline (`relationships.introductoryOffers` + `included`, `${local-id}`s) creates any number at once (175 in about four seconds), all or none: one refused territory fails the whole request. An empty `introductoryOffers` list in a PATCH removes nothing, and there's no bulk delete. A territory's offers can't overlap ("Provided DateRange … overlaps with existing offer's DateRange"; no start date means today, no end date never ends), and it takes one future offer at most ("There is an future intro offer with same country"), so `introductoryOfferConflicts` leaves those territories out first. A paid offer takes a subscription price point per territory (Apple's comparable ones via `equalizations`). Only the end date changes (null clears it). The subscription endpoints don't count against the hourly limit.
- **Bundle IDs (verified live 2026-10-22):** a new bundle ID is always `UNIVERSAL`, whatever `platform` the request names (registered with `MAC_OS`, read back `UNIVERSAL`), and it starts with `IN_APP_PURCHASE` enabled. Only older IDs read `IOS` or `MAC_OS`, and some keep an older App ID prefix (`seedId`) than the team ID. The list takes `include=bundleIdCapabilities` (`limit[bundleIdCapabilities]` up to 50) but not `app` (400 "'app' does not exist"), and included capabilities carry their type but no settings; the capabilities endpoint has the settings, keyed (`DATA_PROTECTION_PERMISSION_LEVEL` → `COMPLETE_PROTECTION`, `PROTECTED_UNLESS_OPEN`, `PROTECTED_UNTIL_FIRST_USER_AUTH`; `ICLOUD_VERSION` → `XCODE_6`), without names. Apple also sends capability types the spec doesn't list (`ENHANCED_SECURITY`). Verified: registering, enabling Data Protection with a setting, changing it with a PATCH of the capability's settings, and disabling it. A wildcard ID is only an identifier ending in `*` (the create request has no type). The developer portal's form allows a description of ASCII letters, digits, spaces, hyphens, periods and apostrophes (50 at most) and a bundle ID of ASCII letters, digits, hyphens and periods (155 at most), a wildcard one ending in `*` (`BundleIDs.isValidName`/`isValidIdentifier`, tested). The portal offers about 120 capabilities; the API takes the 28 in `CapabilityType`.
- **Revoking and Xcode (seen 2026-10-22):** revoking a certificate doesn't touch the keychain, and macOS kept treating two development certificates revoked hours earlier as valid (`security verify-cert -R ocsp -R require` passed), so Xcode still listed them; they have to be removed from the keychain (`security delete-identity -Z <sha1>`). Xcode with automatic signing makes a development certificate of the signed-in Apple ID's own ("Apple Development: <name>") rather than use one created with an API key; with manual signing it makes none. The API doesn't list Developer ID Installer certificates (`CertificateType` has no such case). The developer portal's profile rename makes a new profile (new creation date).
- **Profiles (verified live 2026-10-22):** iOS development profiles hold Macs too (Apple silicon ones run iPhone and iPad apps; an Intel iMac was taken as well), Mac profiles only Macs (`Profiles.fits`). Revoking a certificate made the 25 development profiles that held it INVALID at once (they keep their expiry date). Reissuing (delete, then create with the same name, type, bundle ID and devices) gave each a new UUID and a fresh one-year expiry for development; a new Mac App Store profile expired with its certificates' earliest date (8 Jul 2027), as the other App Store profiles. A profile's certificates list still includes the revoked certificate (`profiles/{id}/certificates`), so a client finds it revoked by comparing with the current certificates. Xcode's own wildcard App IDs have the bare identifier `*` ("XC Wildcard", "Xcode: Mac Wildcard AppID").
- **Certificates (verified live 2026-10-22):** creating takes only the type and the CSR; Apple ignores the CSR's subject and names a certificate after who requested it: the team for distribution and Developer ID, a person for development, and "Created via API" (`Apple Development: Created via API (<pseudo user ID>)`) for one made with an API key. A PATCH takes only `activated`, so the name can't change. `certificateContent` is the DER certificate (base64) on every read. A private key made in the login keychain by another app (`SecKeyCreateRandomKey`, permanent) signs with codesign only after the keychain asks the user to allow codesign to use the key.
- **Custom EULA (`endUserLicenseAgreements`, verified live 2026-10-20):** a PATCH with `territories` replaces the whole list; empty text or an empty territory list is refused (409); DELETE brings back Apple's standard agreement (the app's related GET answers `{"data": null}`). The territories come from `endUserLicenseAgreements/{id}/territories` (limit 200; the include on the agreement caps at 50).
- **App Store Server Notifications endpoints** are app attributes (`subscriptionStatusUrl`/`subscriptionStatusUrlVersion` and the `ForSandbox` pair; verified live 2026-10-20): a URL without its version is refused (409 INVALID_STATE), so `updateApp` sends both, with V2 for a new endpoint; an empty URL fails the URI check, and only sending URL and version as null removes one. Reading the app right after the PATCH still returns the old values for about a second.
- **App languages (verified live 2026-10-22 on a test app):** app info and version localizations stay in step. Creating an app info localization (`AppInfos.createLocalization`, locale + name required) also adds the locale to the version being prepared, and deleting that version localization also deletes the app info's. So adding a language is one app info POST (a version POST after it answers 409 "already exists"), and removing one deletes the version localization first (`VersionLocalizations.delete`, which clears its asset library placements), then the app info localization only if it's still there. Locale codes are `AppInfos.locales`: bare `tr`, `ca`, `ja`, region-qualified `de-DE`, `en-US`, scripts `zh-Hans`.
- **Encryption declarations use top-level endpoint** — `apps/{id}/appEncryptionDeclarations` returns 404 for some apps. Use `appEncryptionDeclarationsGetCollection(query: .init(filterApp: [appID]))` instead. Legacy declarations can report their platform in lowercase (`ios`).
- **Territory availability limit is 50** — The v1 `include: [.territoryAvailabilities]` has a max limit of 50. Use the v2 sub-resource endpoint (`appAvailabilitiesV2TerritoryAvailabilitiesGetToManyRelated`, `limit: 50, include: [.territory]`) and page it with `ASCPaging.allPages`.
- **Multiple AppInfo objects per app** — `appInfos.get()` can return multiple objects (current + replaced). `pickActiveAppInfo()` handles selection: filters out `replacedWithNewInfo`, prefers editable state (prepareForSubmission/waitingForReview) over live. Used by both `findActiveAppInfo()` and `app-info view`. Included localizations must be filtered by the selected AppInfo's `relationships.appInfoLocalizations.data` IDs — back-references on included items aren't populated.
- **`findVersion()` prefers editable versions** — when `versionString` is nil, first queries for prepareForSubmission/waitingForReview versions. If multiple exist (multi-platform apps), prompts user to select by platform. Falls back to latest version if none are editable.
- **Universal-purchase apps hold the same version string per platform** — one app record can have e.g. iOS 5.0 AND macOS 5.0, and iOS/macOS builds can share build numbers. Any lookup by version string or build number must also match platform: `findVersion()` takes a `platform:` param (filters server-side, prompts if still ambiguous), `selectBuild()`/`awaitBuildProcessing()` filter via `buildPlatformFilter()` (`filter[preReleaseVersion.platform]`), and review submissions are matched by `attributes.platform` (one active submission per platform; `selectSubmission()` prompts when several are active). Version-scoped commands expose this via the shared `PlatformOption` option group (`--platform ios|macos|tvos|visionos`, parsed by `parsePlatform()`).
- **AppCategory has no name attribute** — The category `id` IS the human-readable name (e.g. `UTILITIES`, `GAMES_ACTION`). No separate name field exists.
- **Review submissions (verified live 2026-10-20):** the list returns what App Store Connect's App Review page shows (the last 10 completed submissions from 180 days plus any open ones); a completed submission whose items were all removed still reads `COMPLETE` (the item says `REMOVED`); `include=submittedByActor,lastUpdatedByActor` gives `USER` (name, email), `API_KEY` (key ID) or `APPLE`. A draft (`READY_FOR_REVIEW`) can't be canceled (409 "Resource is not in cancellable state") and the API has no DELETE for it, so an empty draft stays (App Store Connect's draft panel offers Delete Submission for an empty one, seen 2026-10-21, but not through the API). App Review's messages (rejection reasons, replies) have no API. An item's relationships are filled in only for the kinds named in `include` (`fields[reviewSubmissionItems]` alone leaves them empty), so `items` includes every kind; `appStoreVersionExperiment` and `appStoreVersionExperimentV2` can't be included together (400).
- **`apps review submit` and a leftover draft:** adding the version to a new submission is where App Store Connect validates it; when that 409s, the empty submission stays behind (READY_FOR_REVIEW, 0 items). A re-run reuses it and now adds the version first when the submission doesn't hold it (items listed with `include: [.appStoreVersion]`, without which the relationship has no ID).
- **IAP/sub submissions 409 without a pending version** — `inAppPurchaseSubmissions`/`subscriptionSubmissions`/`subscriptionGroupSubmissions` POSTs return 409 "has no pending version for submission" for products without pending edits. An APPROVED product with pending edits *stays* APPROVED, so `ProductVersions` (ProductVersions.swift) checks the product's version history instead: `pendingIAP`/`pendingSubscription`/`pendingGroup` query the `versions` sub-resource with `filter[state]` = PREPARE_FOR_SUBMISSION, READY_FOR_REVIEW, REJECTED, DEVELOPER_REJECTED (inferred from the app-version convention, not yet observed on a real pending edit — adjust `pendingStates` if it turns out wrong; groups additionally ignore an unchanged draft, see below). Used by `submitBundledProducts()` in `apps review submit` (candidates are still READY_TO_SUBMIT/APPROVED products; the specific 409 is still caught per item as a safety net), by `iap submit`/`sub submit`/`sub submit-group` (which no longer require READY_TO_SUBMIT — any pending version qualifies, incl. approved products with edits — and stop before any request otherwise), and by `iap info`/`sub info` (`pendingVersion` in text + JSON, nil-omitted). `ProductVersions.reviewItems` resolves review-submission items to app version / IAP / subscription / group; `apps review status` does this for active submissions only (one extra request per product item) and its JSON items gain optional `kind`, `name`, `version`, `versionState`.
- **Product versions model (ASC OpenAPI 4.4.1+, verified live 2026-09-22)** — IAPs, subscriptions, and subscription groups now expose a version history: `GET /v2/inAppPurchases/{id}/versions`, `/v1/subscriptions/{id}/versions`, `/v1/subscriptionGroups/{id}/versions` (each record: `version` int + `state` from PREPARE_FOR_SUBMISSION/READY_FOR_REVIEW/WAITING_FOR_REVIEW/IN_REVIEW/ACCEPTED/APPROVED/REPLACED_WITH_NEW_VERSION/REJECTED/DEVELOPER_REJECTED; `filter[state]` supported). The list endpoints (`apps/{id}/inAppPurchasesV2`, `apps/{id}/subscriptionGroups`, `subscriptionGroups/{id}/subscriptions`) accept `include: [.versions]` + `limitVersions`, but `relationships.versions.data` only hydrates when `versions` is ALSO named in the parent's `fields[...]` (same gotcha as the IAP price schedule). Review submission items reference bundled products as `inAppPurchaseVersion`/`subscriptionVersion`/`subscriptionGroupVersion` relationships (seen on a real submission), and `ReviewSubmissionItemCreateRequest` accepts them. The new v2 localizations (`/v2/inAppPurchaseLocalizations`, `/v2/subscriptionLocalizations`, `/v2/subscriptionGroupLocalizations`) hang off a version and have NO `state` attribute — state lives on the version. A product's pending edits should therefore be detected via a version in a non-APPROVED/non-REPLACED state rather than via v1 localization states (which miss image/screenshot-only edits). Wired via `ProductVersions.swift` (see the 409 bullet below); there is no DELETE for version records.
- **Unchanged drafts:** App Store Connect can keep a product version in PREPARE_FOR_SUBMISSION with nothing changed (seen live 2026-10-07: a subscription group's v2 with localizations identical to the approved v1, invisible in the web UI). The version endpoints are create/read only (no DELETE or PATCH), so such a draft can't be removed through the API. `ProductVersions.pendingGroup` therefore counts a PREPARE_FOR_SUBMISSION group draft only when its localizations (locale, name, customAppName) differ from the latest APPROVED version. IAP and subscription drafts are still taken at face value: their edits can be image or review-screenshot changes that a localization comparison would miss.
- Localizations are per-version: get version ID first, then fetch/update localizations
- Updates are one API call per locale — no bulk endpoint in the API
- Only versions in editable states (`PREPARE_FOR_SUBMISSION` or `WAITING_FOR_REVIEW`) accept localization updates — except `promotionalText`, which can be updated in any state
- `create-version` `--release-type` is optional; omitting it uses the previous version's setting
- **`bundleIDCapabilities` sub-resource rejects `limit`** — despite the generated code accepting `limit: Int?`, the API returns an error if `limit` is passed. Use `.get()` with no arguments.
- **TestFlight endpoints** — `betaAppReviewDetails` always exists per app (PATCH only, no POST); same for `betaLicenseAgreements` (empty `agreementText` = Apple's standard agreement). Internal groups with `hasAccessToAllBuilds` have no explicit build list (skip the builds fetch). On `betaTesters.get`, don't combine `filterApps` with `filterBetaGroups` — the group already scopes to one app. `testflight app-info`, `review-info`, `eula` and `status` and `apps review info` read and write through `TestInformation`, `ReviewInformation` and `BetaReview`. `findBuild()` in TestFlightCommand.swift resolves `--build`/`--platform` to a build (latest non-expired by default, expired allowed when an explicit number is given) with the same cross-platform ambiguity prompting as `findVersion()`.
- **Included resources are capped at 50 per response:** a `builds` page of 200 with `include=buildBetaDetail` came with only 50 `buildBetaDetails` (seen 2026-10-23 on an app with hundreds of builds), so the other 150 builds had no TestFlight states (`testflight builds --limit 200` showed "—" for them up to 0.25.3). `Builds.list` pages 50 at a time. Check the cap whenever a list includes a to-one relationship per item.
- **Review information (verified live 2026-10-23 on a test app):** the contact goes as a whole. A request that sets one contact field must carry all four (first and last name, phone, email; 409 "You must provide a value for the attribute 'contactEmail'"), and a saved one can't be cleared (null refused the same way); `ReviewInformation.changes` sends all four whenever one changes. An App Store record (`appStoreReviewDetails`) refuses every PATCH until its contact is complete, and its phone must start with + and the country code; beta review's record takes notes alone while its contact is empty. A new App Store record reads `demoAccountRequired: true` (App Store Connect's default); a required demo account without a name or password saves fine on both (checked at submission, presumably). Notes, demo name and password clear as null. Test Information fields clear as null too.
- **Recruitment criteria are a legacy setting (seen live 2026-10-23):** App Store Connect no longer shows them (a group's Settings offer "Test iPhone and iPad Apps on Apple Silicon Macs" and "… on Apple Vision Pro" instead, the group attributes `iosBuildsAvailableForAppleSiliconMac`/`iosBuildsAvailableForAppleVision`), and the API can't add them: the spec's `POST /v1/betaRecruitmentCriteria` answers 404 "'/betaRecruitmentCriteria' is not a valid URL", and a PATCH of the group's ID (criteria take the group's ID as theirs; the 409 for a group without them names it) answers 404 "no resource". `criteria set` only changes a group's existing criteria.
- **Recruitment criteria quirks** — `GET betaGroups/{id}/betaRecruitmentCriteria` on a group with no criteria returns HTTP **409** ("BetaRecruitmentCriteria with id '…' does not exist"), not 404 or a null payload — `Criteria.fetch()` maps both 404 and 409 to nil. Unbounded OS limits come back as **empty strings**, not nil. Device-family enum case names (`iphone`, `ipad`, `appleTv`, `vision`) have `formatFieldName` overrides for proper display (iPhone, iPad, Apple TV, Apple Vision).
- **Tester invites need an installable build** — `betaTesterInvitations` POST fails with a clear API error if the tester's groups have no builds assigned; surface it as-is.
- **TestFlight locales ≠ App Store metadata locales** — `betaBuildLocalizations`/`betaAppLocalizations` use TestFlight's own locale set: `tr`, `ja`, `ko` (bare codes) but `en-US`, `de-DE`, `fr-FR` (region-qualified). Creating with `tr-TR` fails with 409 "The 'locale' value is invalid" (verified live). App Store version and app info localizations use bare `tr` too (seen live 2026-10-22; `AppInfos.locales` lists all 50).
- **Beta review is instant for follow-up builds** — only the first build of a version gets a full beta review; later builds of an approved version go straight to APPROVED on submission (verified live: an app's 1.0 build 9 after build 8 was approved).
- Filter parameters vary per endpoint — check the generated PathsV1*.swift files for exact signatures
- **IAP price schedule fetches need fields[] AND include[] for relationships to populate** — Two related quirks discovered when wiring `iap pricing`:
  - The schedule fetch (`inAppPurchasesV2IapPriceScheduleGetToOneRelated`) returns the schedule but `relationships.baseTerritory.data.id` is nil unless you pass `fieldsInAppPurchasePriceSchedules: [.baseTerritory, .manualPrices]` AND `include: [.baseTerritory]`. Both are required.
  - The manual prices fetch (`inAppPurchasePriceSchedulesManualPricesGetToManyRelated`) returns the price records but each record's `relationships.territory.data.id` and `relationships.inAppPurchasePricePoint.data.id` are nil unless you pass `include: [.inAppPurchasePricePoint, .territory]`. Without it you get just resource links.
  - Bottom line: for relationship `data` IDs, always pass both `include` and (where required) the matching `fields[]`. The schedule POST replaces the whole schedule wholesale, so you need these IDs to round-trip existing manualPrices through a read-modify-write.
- **IAP schedule POST is wholesale, but additive in practice** — `POST /v1/inAppPurchasePriceSchedules` fully replaces any existing schedule. To preserve manual overrides across a base-territory change or any edit, fetch the existing schedule first and include all entries you want kept in the new payload. Apple's web UI's "all manual prices will be deleted" warning is UI-conservatism — the API itself preserves whatever you send. The `iap pricing set/override/remove` commands all do this read-modify-write.
- **Subscription pricing is per-territory** — there's no `manualPrices`/`automaticPrices` split like IAPs have. Every entry in `subscription.prices` is an explicit `SubscriptionPrice` you POST. The `--equalize-all-territories` flag on `sub pricing set` mimics the web UI's auto-fill by walking `subscriptionPricePoints/{id}/equalizations` and POSTing one record per territory.
- **`isPreserveCurrentPrice` keeps existing subscribers on their old price** — On `SubscriptionPrice` POST, set `isPreserveCurrentPrice: true` to grandfather existing subscribers when raising prices. Apple's behavior:
  - **Decrease** (new < current): existing subscribers automatically get the lower price; `isPreserveCurrentPrice` is meaningless. `sub pricing set` warns and prompts interactively. Under `-y`, requires `--confirm-decrease` to acknowledge the revenue impact — plain `-y` is not enough.
  - **Increase** (new > current): the dev MUST decide. `--preserve-current` keeps existing subs at old price; `--no-preserve-current` pushes new price after Apple's notification period. The `sub pricing set` command errors if neither flag is passed for any increase (single territory or any territory in `--equalize-all-territories`).
  - **New territory** (no current price): no existing subs to consider; the flag is unnecessary.
  - **Unchanged**: `sub pricing set` skips silently. In equalize mode, only changed territories are POSTed.

### Price export JSON format (used by iap/sub pricing export/import)
```json
{
  "baseTerritory": "USA",
  "prices": { "USA": "4.99", "FRA": "5.99" }
}
```
- `baseTerritory` is present in IAP exports, omitted in subscription exports (sub import ignores it; IAP import falls back to the target's existing base, then USA)
- Import resolves each customer price against the **target** product's own tiers (exact match required; nearest tiers listed on mismatch), so a file can be applied to any product in any app. Territory keys are normalized to uppercase on load.
- IAP import replaces the schedule wholesale — territories not in the file revert to auto-equalize; if the resulting schedule equals the current one it's a no-op. Sub import only touches listed territories, skips unchanged ones, and runs through the shared increase/decrease gates (`gateAndApplyPriceChanges`).
- **Batched tier resolution**: fetching one territory's tier list is ~4 paged calls (limit 200, ~800 tiers/territory), so a 175-territory file would be ~700 requests. `resolvePricePointsBatched` (IAP) / `resolveSubPricePointsBatched` (sub) instead pass 10 territories per `filterTerritory` with `limit: 8000` (accepted by both pricePoints endpoints) — ~18 requests total. Points are grouped via `relationships.territory.data.id`, which requires BOTH `fields[...PricePoints]: [.customerPrice, .territory]` AND `include: [.territory]` (same hydration gotcha as the IAP schedule). Sub import first walks the anchor territory's equalizations — territories whose file price matches the equalized tier resolve with no extra fetch.
- **Transient-error retry**: ASC intermittently returns bursts of HTTP 500s during multi-territory price writes (observed live: 23 consecutive territories failing in one window, all succeeding on retry). `withTransientRetry` (Formatting.swift; `isTransientError` covers 429/5xx and dropped, timed-out or failed connections) wraps the price POSTs — `postSubscriptionPrice` and `postSchedule` — retrying 429/5xx in place (2s/5s backoff); `gateAndApplyPriceChanges` additionally sweeps transient failures in a second pass after a 5s pause, then reports the failed territory list with a re-run hint and exits non-zero. Client-side 4xx errors are never retried. Re-running an import/equalize is idempotent (already-applied territories categorize as unchanged and are skipped).

A classic screenshot whose library placement (same display type group, same position) isn't ACTIVE counts as stuck too ("Pending in the asset library"), which App Review refuses; one extra placement request per set

Verified live 2026-10-07 on two apps × 29 locales: the library ID equals the app ID, placements keep creation order (no ordering request needed), `--replace` deletes the localization's Duo placements (`filter[placementType]` + `filter[placementGroup]`), and sizes are checked locally against the library's image specs (2853×2007, 2007×2853, 2034×1398, 1398×2034; a 1 px-short 2852×2006 is rejected). The classic API lists the Duo set as `APP_IPHONE_DUO`, empty right after upload and with the same screenshots once the placements are ACTIVE, so `media download` skips it, `media verify` lists the placements instead of it, and `media prune` skips display types `ScreenshotDisplayType` doesn't know. Not supported yet: Duo previews (`appAssetLibraryVideos`).
- **Product page header and search results images** (`PRODUCT_PAGE_HEADER/`, `APP_STORE_SEARCH_RESULTS/` folders) also go through the asset library: category `CREATIVE_ASSETS`, placement types `PRODUCT_PAGE_HEADER_ASSET`/`APP_STORE_SEARCH_RESULTS_ASSET`, group `DEFAULT_PROFILE` (display class `DEFAULT`, no device family: one image per localization that the version shows on every device, iPhone, iPad and Duo alike, confirmed in App Store Connect; platform ANY, so `filterPlan` keeps them on every platform's versions). `appAssetLibraryRefData` (read live 2026-10-08) allows one of each per version, custom product page and product page optimization localization; sizes: header PNG 3840×1646 or 5244×2950, search results 3:2 JPG/PNG 1920×1280–3840×2560 or PNG 5244×2950, no alpha, ≤500 MB. Both also take a video (header 3840×1646, search results 3:2; 5–30 s at 30/60 fps). Every library folder is an `AssetLibrary.Slot` (placement type, group, category, `ImageSpec`s, single or ordered, platform); a single slot is always replaced: the new image is uploaded first, then the current placement deleted, then the new one placed. A folder with more than one image in a single slot fails at scan time. Verified live 2026-10-08 on one version localization: both uploads placed and `ACTIVE` within 2 s, `media verify` listed them by file name, and `DELETE /v1/appAssetLibraryPlacements/{id}` then `DELETE /v1/appAssetLibraryImages/{id}` (204 each) emptied the slots and removed the library images (GET 404). Size rejections dry-run tested.
- **Library images outlive their placements; ascelerate cleans up safely.** Deleting a placement leaves its image in the app's asset library (seen live 2026-10-08: replaced Duo images still answered 200 minutes later; Qrafter had 845 unplaced images, 404 from a classic iPhone/iPad `--replace` and the rest from Duo runs). Versions share images (live 2026.16 and 2026.17 place the same Watch Ultra image), and old versions keep INACTIVE placements of ARCHIVED images (checked on 20.0, 20.7 and 1.0 from 2011), so an image with no placement was only ever on deleted placements. `AssetLibrary.removePlacement` (used by `media remove`, Duo `--replace`, single-slot replacement and the end-of-run Duo pass) deletes the placement, then the image only if `isUnused`: no placement at all (read fresh with `include=placements`; a missing list counts as in use) AND an unreviewed state (`AWAITING_UPLOAD`, `UPLOAD_COMPLETE`, `COMPLETE`, `FAILED`, `PREPARE_FOR_SUBMISSION`). Never delete a library image that fails either test: a placed image disappears from that version, the live one included. Classic `--replace` deletes appScreenshots, and the classic API has no link from screenshot to library image, so before clearing a set the upload reads the localization's screenshot placements in the display type's group (`AssetLibrary.classicScreenshotImages`, via `displayTypeGroups`) and afterwards deletes those images `isUnused` allows (`deleteImagesIfUnused`; clearing the set removes its placements at once). Verified live 2026-10-08 on en-US: replacing `APP_IPHONE_67` deleted the 7 old images (404), and replacing `APP_WATCH_ULTRA`, whose APPROVED images live 2026.16 shares, kept all 4 (still placed on 2026.16). Leftovers from earlier runs: `media library --delete-unused` cleans them (list via `appAssetLibraries/{id}/images?include=placements&limit[placements]=1`, 200 per page, ~25 s for 8,066 images; deletes eight at a time, each re-checked, ~70 s for 845). An unplaced image can't say which slot it was in, so `--only` matches kinds by asset category plus a size the slot accepts (`AssetLibrary.image(_:fits:)`, reading `imageAsset` width/height); Qrafter's 845 split cleanly into 435 Duo (2853×2007), 202 iPad 13" (2064×2752), 202 iPhone 6.9" (1320×2868) and 6 sizeless AWAITING_UPLOAD, which match no display type; `UNFINISHED_UPLOADS` selects images with no `imageAsset` (the file never arrived). Display type kinds map to placement groups (`AssetLibrary.displayTypeGroups`, e.g. APP_IPHONE_67 → IPHONE_DYNAMIC_ISLAND_LARGE_PROFILE) whose sizes come live from `appAssetLibraryRefData` (`screenshotSpecs`); the map can't endanger a placed image, since `--only` only narrows already-unused images. Images younger than an hour are never deleted (an upload reserves images before placing them), and a 429 that outlasts the retries stops the batch (the hourly 3,600-request quota is spent; cleaning both Qrafter apps the same day hit it) instead of failing every remaining image. Verified live: Duo `--replace` and header replacement left the old images 404; `media remove` emptied the slot and deleted the image.
- **Asset library videos** (`appAssetLibraryVideos`, verified live 2026-10-08): reserve with category + file name + size, PUT the upload operations, commit `uploaded: true`, place with a `video` relationship. Slots carry `videoPlacementType`/`videoSpecs`: the header and search results take a video under their own placement type (one image OR video per locale), and `APP_IPHONE_DUO/` videos are Duo app previews (`APP_PREVIEW`, 1920×886 or 886×1920, 15–30 s, 23–30 fps, audio required). `AssetLibrary.validateVideo` checks size, length, frame rate (29.97 counts as 30) and audio with AVFoundation. Placements of a still-processing video read `PENDING` (not in the spec) and the video `UPLOAD_COMPLETE`; verify counts only ACTIVE/INACTIVE/PARENT_* as complete. Library videos report no pixel size of their own (their `previewFrameImage` poster has one, about a minute after upload), and `videoAsset` is an HLS playlist (`.m3u8`) that fills in only seven to nine minutes after upload (seen live 2026-10-20; empty before that, which earlier looked permanent), so `media download` can't fetch header/search videos as files (Duo previews come from the classic preview mirror) and `media library` matches videos (and images) by `specId` against `appAssetLibraryRefData` (`AssetLibrary.specIDs`, `placementTargets`; verified to select exactly the 2853×2007 Duo images). Classic previews are library placements too (`APP_PREVIEW` in the display type's group), so classic preview `--replace` cleans up their videos like screenshots (verified: "Deleted 1 existing preview and 1 unused library video", old video 404). The classic API mirrors Duo screenshots and previews as `IPHONE_DUO` sets (it created an empty `IPHONE_DUO` preview set on its own); verify, download and prune skip those. `media remove --previews` removes Duo previews. Custom product pages: `AssetLibrary.Owner` (`.versionLocalization`/`.productPageLocalization`) picks the placement relationship and listing endpoint; `product-pages media upload` routes `--display-type`/`--preview-type` slot names to `uploadAndPlace`, `media list` adds library placements (`slotPlacements`), `media delete` takes a placement ID. Verified live 2026-10-08 on a custom product page: header image, search results video and Duo screenshot placed on its en-US localization, a second header replaced the first (old image 404), and `media delete` by placement ID removed each with its library file (404). Test videos for live checks: a scratch AVAssetWriter tool rendering a still image to H.264 at exact size, length and fps, with silent AAC when audio is required.
- **Duo upload robustness (first real run, 2026-10-07: 12 of 203 files on one app failed with lost connections, timeouts and TLS errors, each leaving a gap mid-locale):** every asset library call retries transient errors (`withTransientRetry`, network errors included). A repeated image reserve can at worst leave an unplaced library image, but a repeated placement POST would show the screenshot twice, so `placeScreenshot`'s retry first looks for a placement of the same image (`filter[image]` on the localization's placements, verified to return exactly that placement). A set that still ends with failed files is placed again at the end of the run (`DuoRedo`): this run's placements are deleted (earlier ones stay) and every file is uploaded and placed again in order.
- **Duo verify:** `fetchAllMediaStatus` lists each localization's Duo placements (sorted by `placementGroupPosition`) with their images included, for the file names (`AssetLibrary.placementsWithMedia`, one request per slot and locale; `media download` and classic `--replace` read placements the same way). The placement list with `include=image` answered HTTP 500 every time on 2026-10-07, so this used to cost one request per placement; it works again since (seen 2026-10-21). A placement reads `ACTIVE` when done. With a folder, `placementSetsDifferingFromFolder` flags locales whose Duo file names in display order differ from the folder; stuck or misordered Duo screenshots are fixed with `media upload --replace`, not by verify's classic retry. `/v1/appAssetLibraryPlacements/{id}/image` answers 403.
- **Spec bug (metrics):** a metric response's dimension named after a resource (`betaTesters` in `apps/{id}/metrics/betaTesterUsages`) is declared as a string `data`, but Apple sends the linkage `{"type", "id"}` (seen 2026-10-23). The prepare script turns those six dimensions into linkage objects (Game Center's `result` dimensions stay strings, unverified); `openapi.json` was patched the same way by hand, since Apple's download wasn't at hand. Metric dates (`start`, `end`) come as plain days, which the date transcoder accepts.
- **Spec bug:** Apple's `AppAssetLibraryPlacement.relationships` is a `oneOf` discriminated by `mediaType`, which Apple sends in `attributes`, so any response with placement relationships failed to decode. The prepare script turns a discriminated `oneOf` whose property no branch declares into an `anyOf` (the only such schema in 4.5.1); the image ID is `relationships?.value1?.value2.image?.data?.id`.
- **Upload progress:** each `media upload` file line starts with `[n/total]` for the whole run (`UploadCounter`; the end-of-run Duo pass numbers its own files). `uploadChunks` (core) reports each file's bytes as its chunks are acknowledged (`progress`; URLSession's sent-bytes callbacks run megabytes ahead of the network, and only go to the optional `sending`, with the chunk sizes to `chunks`) to the observer that the task-local `UploadProgress.observe` makes; `main()` binds it to `UploadProgressLine.observe` for the whole run. On a terminal (`isTerminal`) that draws live byte progress after the line's text (`UploadProgressLine`: saves the cursor with `ESC 7`, redraws with `ESC 8` + clear-to-end on each percent change, erases on finish so the caller's "Done." lands as before). Every asset upload gets it, since they all go through `uploadChunks`; a `run-workflow` in a terminal shows it too, while piped output and CI logs stay plain. Verified in a pty on a live Duo upload: screenshots finish in one to three redraws, so it matters mostly for previews.
- **Chunk uploads run one at a time by default** (`UploadOptions.parallelChunks`, a task-local `main()` binds from `ASCELERATE_PARALLEL_CHUNKS`: four at once saturated a slow uplink, starving other traffic, and four chunks finished together; `uploadChunks` via `boundedConcurrentMap`; each chunk reads its own slice with its own file handle; the core's `ChunkProgress` sums acknowledged chunks) **and retry 429/5xx and network errors** (honoring `Retry-After`, 4 attempts; a chunk PUT is safe to repeat, and `uploadAsset` also retries the commit PATCH): the storage host rate-limited a burst live after ~180 sequential uploads. `uploadChunks`/`uploadAsset` are generic over `UploadOperationDescribing`, which ASCKit's `UploadOperation` adopts.
- File matching: server position N = Nth file alphabetically in local `locale/displayType/` folder

## Screenshot Module (`ascelerate screenshot`)

Captures App Store screenshots from iOS/iPadOS simulators. Replaces fastlane snapshot.

### Architecture

```

    ScreenshotTestRunner.swift   # xcodebuild wrapper: build-for-testing + test-without-building
```

### Flow

1. `build-for-testing` with `generic/platform=iOS Simulator` and `-configuration` (default Release)
2. xcodebuild writes to project's actual derived data (custom `-derivedDataPath` is ignored by Xcode workspace settings)
3. Resolve xctestrun file from `~/Library/Developer/Xcode/DerivedData/{ProjectName}[-hash]/Build/Products/`
4. For each language: boot all simulators → silence system noise (see below) → wait (`waitAfterBoot`) → set dark mode → localize → override status bar → uninstall app (`reinstallApp`) → `test-without-building` concurrently per device → collect screenshots
5. Each device gets isolated cache at `~/Library/Caches/tools.ascelerate/{UDID}/`
6. ScreenshotHelper.swift uses `SIMULATOR_UDID` env var to find its cache directory
7. Errors skip failing device/language, error logs saved as `{language}/{device}-error.log` (unless `stopAfterFirstError`)
8. Summary table printed at end

### Key decisions

- `-parallel-testing-enabled NO` prevents simulator cloning (needed for status bar override)
- **System noise suppression (`ScreenshotRunner.silenceSystemNoise`, right after the first boot in prep, both localize and plain branches).** Verified live on an iOS 26.5 probe 2026-09-10: (1) The iOS 26 "Ready for Apple Intelligence" banner is a `followupd` item (section `com.apple.Preferences`) that `generativeexperiencesd` posts as soon as the model catalog reports ready (1 s after boot when the host's models are ready, minutes later otherwise) and records in `com.apple.generativeexperiences.corefollowup` / `DateOfLastAppleIntelligenceReadinessCFU`; stamping that key with "now" via `simctl spawn defaults write … -date` before the real boot suppresses it (0 posts vs. 1 in control). Apple Intelligence itself can't be turned off on the simulator: `eligibilityd` force-answers eligible with `OS_ELIGIBILITY_CONTEXT_FORCE_REASON = Simulator`, so no input/region trick works. iOS 27 no longer posts the follow-up. Turning Siri off (`com.apple.assistant.support` / `Assistant Enabled`) does NOT stop the asset downloads. (2) `disableAssetDownloads` runs `launchctl disable user/<uid>/com.apple.mobileassetd` + `bootout` inside the simulator; the disable persists across reboots (erase resets it) and kept the MobileAsset store at 0 bytes where the control pulled ~1.2 GB (Siri Understanding) + ~460 MB (LinguisticData) per fresh simulator. The foundation models themselves are never downloaded into the simulator; it borrows the host's.
- **Xcode 27 writes a dangling `UITargetAppPath` into the xctestrun** when another project in the workspace has a target with the same name as the UI test's `TEST_TARGET_NAME` but a different `PRODUCT_NAME` (e.g. an iOS `MyApp` target building "MyApp.app" and a macOS `MyApp` target with `PRODUCT_NAME = "My App"` → the xctestrun references "My App.app"). xcodebuild then fails the runner instantly, blocks on `simctl diagnose --timeout=600` (a silent 10-minute stall per run, during which SIGTERM is deferred, so Ctrl-C only lands after the wait), and only then runs the tests with the correct app it already mapped from `DependentProductPaths`. `ScreenshotTestRunner.prepareXctestrun` detects the missing app, substitutes the single other `.app` in `DependentProductPaths`, and writes a repaired copy with `__TESTROOT__` made absolute to `~/Library/Caches/tools.ascelerate/xctestrun/` (kept out of Products so the newest-xctestrun discovery never picks it up). Not deterministic: of two clean Xcode 27.0 RC builds of the same workspace, the first wrote the wrong path and the second the right one; Xcode 26.6 always wrote the right one. Verified live 2026-09-10.
- **The app under test runs with `OS_ACTIVITY_MODE=disable`** (added to `UITargetAppEnvironmentVariables` by `prepareXctestrun`, unless the project sets it): XCTest's automation logs every element query inside the app ("Current tree:", "Fetching AX attributes", "faulted in {…}"), and Xcode captures that into the result bundle. Measured 2026-10-09 on a query-heavy UI test (large accessibility trees, `descendants(matching: .any)` lookups): 3.1 MB per device run as built, 2.7 KB with the variable, same pass and duration. The flood is what made Xcode 27.1's importer crash (below). `OS_ACTIVITY_DT_MODE=NO` alone cut only about a quarter.
- **`-collect-test-diagnostics never`, and a passed run survives an xcodebuild crash.** Seen live with Xcode 27.1 on 2026-10-09: after a passing test, xcodebuild's result bundle importer died (`CASTreeDataStructure/Importer.swift:131: Fatal error … Unable to write data for …/Diagnostics/…/StandardOutputAndStandardError-<bundle id>.txt due to resourceChanged`) because the app was still running and writing to its captured console output (14 MB). The crash counts as a failure, so xcodebuild then ran `simctl diagnose --timeout=600`, a 10-minute stall. The test step now passes `-collect-test-diagnostics never` (accepted with `-xctestrun`, verified), and when xcodebuild exits non-zero but the log's last `Test Suite 'All tests'` line says passed (and no `** TEST EXECUTE FAILED **`), `ScreenshotTestRunner` counts the device as passed with a warning: the screenshots are written during the test.
- `xcrun simctl bootstatus` waits for full boot before applying status bar override
- **Xcode 27 removed Simulator.app.** Simulator windows are now hosted by `<Xcode>/Contents/Applications/DeviceHub.app` (bundle ID `com.apple.dt.Devices`); Xcode ≤26 ships `<Xcode>/Contents/Developer/Applications/Simulator.app`. `open -a Simulator` resolves by name via LaunchServices and fails once no Simulator.app is registered. `SimulatorManager.launchUIHost()` resolves the host inside the `xcode-select -p` Xcode (DeviceHub first, then Simulator.app, then bundle-ID fallbacks); failure only prints a warning and the run continues headless. **DeviceHub does not open windows for booted devices on its own** (Simulator.app did): launching it only shows its device-management window, `-CurrentDeviceUDID` is ignored, and there is no AppleScript/CLI. The only hook is its URL scheme: `open -a <DeviceHub.app> "devices://device/open?id=<udid>"` opens (or focuses) that device's window — `SimulatorManager.showDeviceWindow(udid:)` calls it after every boot in `prepareDevicesConcurrently` (no-op for Simulator.app). Nothing else depends on the app: every other step goes through `xcrun simctl` (CoreSimulatorService), verified live with DeviceHub on Xcode 27.1 (2026-09-22): boot, status_bar, ui appearance, spawn, io screenshot, and full XCUITest runs.
- Test output goes to log files (not stdout) to prevent interleaved output from concurrent devices
- Helper version tracked via `// ScreenshotHelperVersion [X.Y]` comment in generated file (`CreateHelper.installedVersion(at:)`, shared by doctor and setup-prompt)
- **`setup-prompt` is the onboarding path:** it prints instructions for an AI coding agent (UI test target, helper, a `-ASC_SCREENSHOT` screenshot mode with demo data, the tests, the configuration, optional device frames the user downloads from Apple), opening with what the project already has, so re-running it shows what's left. Both prompts tell the agent to talk in the Mac's preferred language (`Locale.preferredLanguages`), since the English instructions would otherwise set the conversation's language. `--design` covers a web app that renders framed screenshots into App Store images and exports `<locale>/<display type>/NN_name.png` for `apps media upload`. The prompts are embedded in the binary so they always match its helper and commands: update them with any change to the helper, the configuration or these commands.
- **`--json-events`** (run) prints one JSON object per line on stdout (`start`, `build`, `language`, `device` steps preparing/ready/testing/retrying/passed/failed/collected, `finished` with results) and moves the readable log to stderr (`EventOutput`, a task-local shared with `builds archive`/`upload --json-events`); stdout is line-buffered for every command so piped readers see lines as they're printed. `doctor --json` prints `{config: {scheme, devices, languages, outputDirectory}?, checks: [{name, status: pass|warn|fail, detail}]}`.
- `clearPreviousScreenshots` only clears per-language after all devices succeed
- `numberOfRetries` — retries failed languages by erasing the failed simulators, re-localizing, rebooting, and rerunning tests. Works around simulator localization bugs where translated labels aren't found. Only failed devices are retried.
- `testplan` and `xcargs` are passed to both build and test phases
- `disableAnimations` passes `-ASC_DISABLE_ANIMATIONS YES` as a launch argument; app must call `disableAnimationsIfNeeded()` to act on it
- SIGINT handler (via `sigaction`) forwards Ctrl-C to child xcodebuild processes
- **Helper uses `app.windows.firstMatch.screenshot()`, not `app.screenshot()` or `XCUIScreen.main.screenshot()`.** XCUIScreen captures the simulator framebuffer via the render server, so if the target app has terminated at the moment of capture (seen intermittently on iPad when the last test tap triggers a locale-dependent crash in the app), the call silently returns a home-screen PNG and the test "passes" with a bad screenshot. `app.screenshot()` detects the dead app but composites a broken buffer on rotated simulators (portrait frame with landscape content pasted un-rotated and cropped — unrecoverable). The window screenshot is still an RPC into the target process — if the process is gone it throws `Lost connection to the application (pid N)`, XCTest marks the test failed, and `numberOfRetries` retries the device+language automatically — and it returns complete rotated content, merely orientation-tagged. Since PNG has no orientation metadata (`pngData()` drops non-`.up` tags), the helper bakes the orientation by re-rendering before saving. Do not switch capture APIs without preserving both the dead-app detection and the rotation handling.
- **iPhone Duo hinge (`setHinge(.open/.closed)`, ScreenshotHelper 1.3).** Xcode 27.1 has no simctl or XCTest API for the hinge. DeviceHub's slider sends a vendor-defined HID event (usage page 0xFF61, usage 0x5B) whose payload is a keyed record `{provider: "com.apple.Virtualization.VirtualMachines", source: "hinge-slider-control", type: "range", value: <degrees>}` (encoding documented in the helper); locationd's `CMDeviceStateRelayManager` turns it into `kIOHIDEventTypeHingeAngle` and SpringBoard lights the matching panel. Any guest process, the XCTest runner included, can register a `HIDVirtualEventService` (private `HID.framework`) of that shape and dispatch the event, so the helper does it in-process: no host-side helper, no clang, no config key. Protocol as measured by baguette (github.com/tddworks/baguette). Verified live on iOS 27.1 2026-10-06: 180° → `openFlat`, 0° → `fullyClosed` (SpringBoard logs `DCMPose: …` under `com.apple.SpringBoard:DevicePose`), a direct jump works (no sweep), SpringBoard settles in ~1.5 s (helper sleeps 2 s), and the hinge resets to closed on every boot. Unfolded captures are 2852×2006 landscape, upright; folded ones 1398×2034. The runner's `userInterfaceIdiom` stays `.phone` while unfolded apps lay out like iPad; tests detect the Duo via `SIMULATOR_MODEL_IDENTIFIER == "iPhone19,4"`. The delegate methods are `nonisolated` because HID calls them off-main (test targets may default to MainActor isolation).
- **Multi-bezel framing.** `deviceBezel` decodes a string or a list (`Device.deviceBezels`). `ScreenshotFramer.bestBezel` picks, per screenshot, the bezel whose detected screen area is closest in size; a portrait bezel is compared rotated for landscape shots (what `composite` does) and loses ties to a native landscape bezel; a landscape bezel never frames a portrait shot. One bezel behaves as before.
- **CGContext rotation direction is counterintuitive**: `rotate(by: -.pi/2)` in CG's y-up coordinate space appears *clockwise* in the displayed image. `ScreenshotFramer.rotated90CCW` (used to rotate the portrait bezel for landscape framing, Dynamic Island to the left = landscapeLeft) uses `translateBy(x: height, y: 0)` + `rotate(by: .pi/2)` for a true displayed-CCW rotation. Verify any rotation change empirically with a marker-pixel test image — the angle sign misleads.

### Markdown for agents (2026-08)

Every docs page has a `.md` twin served via `Accept: text/markdown` content negotiation (same workspace-wide pattern as the sites under `~/Developer/Web` — see that workspace's CLAUDE.md; reference implementation: keremerkan.dev):

- `website/scripts/generate-md-twins.mjs` copies all docs source `.md` files (all 6 locales) into the build output at their route paths (`/docs/<page>.md`, `/de/docs/<page>.md`, …). It runs as part of `npm run build` — **the Pages build command must stay `npm run build`**, not `docusaurus build`, or twins won't generate.
- `website/functions/_middleware.js` (Cloudflare Pages Function) does the negotiation: markdown-accepting requests get the twin with `Content-Type: text/markdown; charset=utf-8`; HTML responses get `Vary: Accept`. Pages HTML is never edge-cached, so there is no Vary/cache-poisoning risk here.
- `website/static/index.md` is the **hand-written** homepage twin — update it when the homepage copy in `src/pages/index.tsx` changes. Docs twins are verbatim source and need no maintenance.

The upload left a second, orphaned AWAITING_UPLOAD record of the same build (24 s apart, the first one), and so do altool and Xcode uploads: on 2026-10-13 the account's apps held 91 such records back to 2025-09, nearly one per past upload, each next to a COMPLETE record of the same build (deleted with `--delete-stale`).
